# 跨设备同步（同步码 + 端到端加密）设计

> 状态：设计稿 v2（2026-11-18）。用户已批方案：不做账号，用同步码加端到端加密，服务端只存密文。v2 按两路对抗审查（grok 18 条、sol 33 条）重写，处置见第 20 节。实现前须再过一次对抗审查。
> 本文所有标注「写死」的地方是三端（Swift、Kotlin、服务端 Python）逐字节一致的契约，实现者不得自选。

## 0. 相对 v1 的主要变化

- 数据模型改为与现有代码同形：收藏与屏蔽成对记账、互斥投影；删除「不感兴趣」房间集合；口味只同步「不想看」（`vetoed`）的 `t:` 与 `g:` 键；收藏顺序不再单独存，由收藏时间推出。
- 每项版本从「设备墙钟毫秒」改为混合逻辑时钟（HLC）。
- 墓碑永不按时间清理。
- 写入认证从长期 bearer 改为 Ed25519 签名；删除与换码在服务端留退役行，旧版本号不复用。
- 同步状态单独持久化，成为同步开启期间的唯一事实来源；本地收藏文件与口味画像中的「不想看」是它的投影。
- 加入、换码、清除、关闭四个流程各自写成可恢复的步骤；字节级格式与金样本字段全部写死。

## 1. 目标与边界

- 同步：收藏、屏蔽、口味里的「不想看」标签与性别、两个设置（`publicOnly`、`infoAlwaysOn`）。
- 不同步：命中与落空证据（hit/miss）、停留、最近看过（seen）、每日命中率、学习暂停开关、「不感兴趣」产生的落空、收藏带来的命中加权、手动加强的权重、观看账本、缩略图缓存、窗口与透明度类设置、音量、`muted`、`phoneDual`、`pipAutoEnter`。理由：量大、与设备相关，或远端改动会在本机产生意外后果（远端 `muted=false` 会让当前设备突然出声）。
- 不做：账号、找回、分享给他人、服务端可读的任何字段、实时推送、轮询、常驻连接、第三方依赖。
- 可见延迟承诺：远端改动在本机「下次启动或回到前台、打开收藏或口味面板、点立即同步」时出现；两台设备都停在前台且无上述动作时，不保证看到对方改动。这是「无轮询」的直接代价，写进隐私与帮助文案。
- 服务端地址不进公开仓：Apple 端经本地、不入库的 xcconfig 注入，安卓经本地 gradle 属性注入，同步码里也带地址。构建分两种情况：
  - 构建未启用同步功能（编译开关关）：完全没有同步入口。
  - 启用了同步功能但没有默认地址：隐藏「创建」，保留「加入」，地址只从同步码取。主机名不保密，不当访问控制。

## 3. 版本号体系（四个互相独立）

| 名称 | 现值 | 出现在 | 改变它意味着 |
|---|---|---|---|
| 同步码格式与密钥派生代 | `vela2` | 同步码前缀、HKDF info | 同一个 `K` 会派生出不同空间：只能经换码流程（第 12.5 节）迁移 |
| 封装版本 | `e1` | 信封前缀、AAD | 新算法或新压缩方式；旧客户端遇到未知前缀进入只读 |
| 文档 schema 主版本 | `2` | 明文 `schema` 字段 | 合并语义变化；旧客户端遇到更大值进入只读 |
| 服务端 API | `/v2` | 路径 | 旧路径保留到所有客户端升级 |

同一主版本内新增字段只能是「字符串叶子」寄存器（第 7 节），旧客户端可以不理解地原样合并保留。

## 4. 密钥、派生与同步码（写死）

### 4.1 主密钥与派生

- `K`：32 字节，由系统 CSPRNG 生成（Apple `SecRandomCopyBytes`，安卓 `SecureRandom`）。随机源报错即中止，不得退化。
- HKDF-SHA256（RFC 5869），三次独立调用，参数相同：IKM = `K`；salt = 32 个 `0x00` 字节（显式传入，不传空 salt）；L = 32。
  - `blobID` = 小写 hex(HKDF(info = ASCII `vela-sync/v2/id`))，64 个字符。
  - `encKey` = HKDF(info = ASCII `vela-sync/v2/enc`)，AES-256-GCM 密钥。
  - `signSeed` = HKDF(info = ASCII `vela-sync/v2/sign`)，RFC 8032 Ed25519 私钥种子。
- 安卓手写 HKDF：PRK = HMAC-SHA256(key = salt, data = K)；OKM = HMAC-SHA256(key = PRK, data = info ‖ `0x01`)。L = 32 只需一个块。
- Apple：`HKDF<SHA256>.deriveKey(inputKeyMaterial: SymmetricKey(data: K), salt: Data(count: 32), info: Data(info.utf8), outputByteCount: 32)`。
- 公钥 `pub` = RFC 8032 编码的 32 字节 Ed25519 公钥。Apple：`Curve25519.Signing.PrivateKey(rawRepresentation: signSeed).publicKey.rawRepresentation`。安卓（API 33 起有平台 Ed25519）：私钥用 PKCS#8 DER 前缀 `302e020100300506032b657004220420` 加种子经 `KeyFactory.getInstance("Ed25519")` 导入。安卓上从种子求公钥的平台路径未验证，列为 S4 探针（第 19 节）。
- 短指纹 = `blobID` 前 8 个 hex 转大写，按 4-4 用 `-` 连接（例 `3F9A-0C21`）。两台设备对码用；它不是秘密，日志也只记这一段。
- 不再有 `writeToken`。

### 4.2 编码规则

- base64url：RFC 4648 §5 字母表，不补 `=`。解码器拒绝 `=`、空白、字母表外字符，以及末位未用比特不为 0 的非规范编码（实现：解码后重新编码必须与输入逐字节相等）。
- hex：一律小写；解析时拒绝大写。
- 十进制整数：无前导零（`0` 本身除外）、无正负号，范围 0 到 2^53−1。

### 4.3 同步码

- 格式：`vela2:` + k43 + `.` + c6 + `@` + origin。
  - k43 = base64url(`K`)，必须正好 43 个字符，解码必须正好 32 字节。
  - c6 = 小写 hex(SHA-256(ASCII(`vela2:` + k43 + `@` + origin)) 的前 3 字节)，用于发现抄错、截断、改主机名。
  - origin 必须规范：`https://` + host + 可选 `:` + port。host 为小写 ASCII 的 DNS 名（标签只含 `a-z0-9-`，不以 `-` 开头或结尾，至少含一个点，总长不超过 253）；拒绝 IP 字面量、非 ASCII（国际化域名须为 punycode）、userinfo、路径（含单独的 `/`）、query、fragment；端口为 1 到 65535 的规范十进制，`:443` 视为非规范，拒绝。
- 解析任一条不满足即报「同步码无效」，不尝试修正（修正会把一位之差变成另一把合法密钥）。
- 请求地址 = origin + `/v2/...`。客户端不跟随任何重定向（3xx 当错误），不带 cookie，不用 URL 缓存，User-Agent 固定为 `Vela-Sync/2`。
- 二维码内容与文本相同。v2 只要求复制、粘贴；二维码显示是可选项。
- 复制时标记敏感：iOS `UIPasteboard` 设 `localOnly` 与 120 秒 `expirationDate`；macOS 同时写 `org.nspasteboard.ConcealedType`；安卓 API 33 起设 `EXTRA_IS_SENSITIVE`。界面、日志、崩溃报告、诊断信息里禁止出现整段同步码、`K` 或完整 `blobID`。

## 5. 混合逻辑时钟（HLC，写死）

- 每台设备在每个同步空间里持久化 `(l, c, dev)`：`l` 为毫秒（48 位）、`c` 为计数（16 位）、`dev` 为加入该空间时随机生成的 32 位设备号（`0x00000000` 保留不用）。
- 线格式：24 个小写 hex = 12 位 `l` + 4 位 `c` + 8 位 `dev`。三段定宽，所以字符串字节序等于元组 `(l, c, dev)` 的字典序。
- 本地事件（一次用户操作取一个 tick，同一操作写的多个寄存器共用这个值）：`pt` = 本机墙钟毫秒；`pt > l` 时 `(l, c) = (pt, 0)`；否则 `c < 0xFFFF` 时 `c += 1`；否则 `(l, c) = (l + 1, 0)`。新值先随同步状态落盘，再用于寄存器。
- 收到远端文档（已通过校验）：取其中所有 HLC 的最大 `(l', c')`；若 `(l', c') > (l, c)` 则令 `(l, c) = (l', c')`。收到时不 tick。由此，看见远端操作之后的本地操作必然排在它之后。
- 时钟回拨：`l` 已持久化，墙钟回拨时走「计数加一」分支，不会生成更小的时间戳。同一毫秒内连续操作靠 `c` 分出先后，先删后加不会丢。
- 远端时间超前：
  - 远端 HLC 的 `l` 超过本机墙钟 24 小时以内：照常合并。
  - 超过 24 小时但在 366 天以内：照常合并并推进本机时钟（不钳制。钳制会让各设备改写出不同的值，合并就不收敛），诊断页记一条「某台设备时钟偏快」。HLC 的正确性不依赖物理时间准确，只会让并发冲突的胜负偏向时钟快的设备。
  - 超过 366 天：整份远端文档按非法处理（第 7.3 节），不合并、不推送，界面提示「云端数据含异常时间，请检查各设备时间」。这一条防止接近 48 位上限的值把时钟顶死。
- 本机墙钟检查：服务端每个 JSON 响应带 `now`（服务端毫秒）。本机与之相差超过 24 小时时暂停一切写入，提示「本机时间不准，校准后再同步」，从源头阻止错时钟设备写入。服务端可以借此谎报阻止同步，这属于可用性攻击，它本来就能拒绝服务。
- 设备号只要求在一个空间内唯一：10 台设备的碰撞概率约 1e-8，碰撞时最坏结果是同一 HLC 上出现两种取值，由第 6.2 节的平局规则确定性裁决。

## 6. 同步文档（加密前的明文）

### 6.1 结构

```json
{
  "schema": 2,
  "rooms": {
    "alice":   { "f": "0193b2c4d5e60000a1b2c3d4+", "b": "0193b2c4d5e60000a1b2c3d4-", "n": "0193b2c4d5e60000a1b2c3d4Alice" },
    "bob_x":   { "b": "0193b2c4d5e70001a1b2c3d4+" }
  },
  "veto": {
    "t:asian": "0193b2c4d5e80000a1b2c3d4+",
    "g:m":     "0193b2c4d5e90000a1b2c3d4-"
  },
  "settings": {
    "publicOnly": "0193b2c4d5ea0000a1b2c3d41"
  }
}
```

### 6.2 寄存器

- 所有寄存器都是字符串 = 24 位 HLC + 载荷。合并取 UTF-8 字节序较大者。HLC 在前，所以先比时间，时间相同才比载荷。
- `rooms.<键>.f`（收藏）与 `.b`（屏蔽）：载荷 `+`（在）或 `-`（不在）。同一 HLC 上 `-`（0x2D）大于 `+`（0x2B），即同刻删除胜。
- `rooms.<键>.n`（显示用大小写）：载荷为用户名原文，小写后必须等于键。只在原文大小写与键不同时写。
- `veto.<键>`：载荷 `+`（不想看）或 `-`（已撤销）。
- `settings.<键>`：v2 已知键 `publicOnly`、`infoAlwaysOn` 载荷为 `1` 或 `0`（同刻 `1` 胜）；未知键载荷为任意字符串，原样保留。
- 缺失的寄存器等价于「HLC 全 0、载荷 `-`」，参与比较时小于任何真实寄存器。
- 一个集合项只需一个寄存器：v1 的 `(a, d)` 取各自最大值后「`a > d` 即存在」，等价于「四个时间里最大的那个是加入」，正好是 LWW 寄存器。体积减半，语义不变。

### 6.3 键规则

- 房间键：用户名小写后必须匹配 `^[a-z0-9_]{2,30}$`（与 `Room.isValidUsername` 同一字符集与长度）。本地不合规的旧名字不进同步，只留在本机。
- 口味键：`t:` + 标签，或 `g:` + `f|m|t|c`（`Gender` 的 rawValue）。标签部分为 1 到 64 个 Unicode 标量，不含 U+0000 到 U+001F、U+007F，首尾不含空白。
- 同步层不重新规范化口味键：按本机 `Belief` 键逐字节同步（Swift `lowercased()`，Kotlin `lowercase(Locale.ROOT)`）。标签来自站点接口，三端拿到的是同样的字节，结果在 ASCII 范围内一致；极少数非 ASCII 大小写映射的差异只会多出一个键，不会丢失或互相覆盖。不做 NFC 等价合并，理由是本机 `Taste` 本身也不做，同步层做了反而与本机键对不上。金样本收入一个非 ASCII 标签用例。

### 6.4 本地操作到寄存器的映射（写死）

每行一个 tick，记作 `h`。「写 X」= 把寄存器 X 设为 `h` + 载荷。

| 本地操作（现有函数） | 同步写入 |
|---|---|
| `Curation.favoriting(x)`、`restoringFavorite(x)` | `f = h+`，`b = h-`，大小写不同时 `n = h` + 原文 |
| `Curation.unfavoriting(x)` | `f = h-` |
| `Curation.blocking(x)` | `b = h+`，`f = h-`，按需写 `n` |
| `Curation.unblocking(x)` | `b = h-` |
| `Curation.importing(names)` | 对每个此刻不在收藏、也不在屏蔽里的名字按收藏处理；从列表末尾往前逐个 tick，文件里第一个名字最新 |
| `Taste.vetoing(k)` | `veto.k = h+` |
| `Taste.restoring(k)`、`boosting(k)`、`removing(k)` | 本机该键 vetoed 或寄存器为 `+` 时写 `veto.k = h-`；否则不写 |
| `Taste.resettingProfile()`、`erased()`（清除全部偏好） | 对每个寄存器为 `+` 的键写 `veto.k = h-`（全部共用一个 `h`） |
| 设置页切换 `publicOnly`、`infoAlwaysOn` | `settings.k = h` + `1`/`0` |
| `rejecting`、`following`、`recording`、`settingPaused`、`marking(seen:)` | 不写 |

- 收藏时一并写屏蔽的 `-`（反之亦然）就是成对记账。它覆盖的情况是：对方有一条本机还没见过、时间更早的屏蔽。只写 `f+` 的话，互斥投影眼下仍显示收藏，但用户之后取消收藏时那条旧屏蔽会冒出来。
- 只有用户操作产生寄存器写入。读取失败返回的空值、只读状态、坏文件改名备份、300 上限裁剪、`Taste.trimmed` 裁剪，一律不产生写入。

### 6.5 投影（同步文档 → 本机视图；不写回文档）

- 收藏中：`f` 为 `+`，且 `b` 不为 `+` 或 HLC(`f`) > HLC(`b`)。
- 已屏蔽：`b` 为 `+`，且 `f` 不为 `+` 或 HLC(`b`) ≥ HLC(`f`)。即两边都在时 HLC 大者胜，平局屏蔽胜。诚实客户端的同一操作不会让两者同为 `+` 且 HLC 相同，平局规则只为保证确定性。
- 顺序：按生效寄存器的 HLC 降序（最新在前，与 `Curation` 的数组语义一致）；HLC 相同时按键的 UTF-8 升序。
- 显示名：有 `n` 用它的载荷，否则用键。
- 本机 `Curation` = 收藏、屏蔽各取投影的前 300 个，加上本机不合规、不进同步的旧名字（排在末尾）。超出 300 的项留在同步文档里，本机不显示；用户再次收藏它会得到新 HLC 并排到最前。裁剪不产生墓碑。
- 口味：`veto` 为 `+` 的键，本机按 `Taste.vetoing(k, now)` 应用；为 `-` 且本机该键 vetoed 时按 `Taste.restoring(k, now)` 应用。两者都不产生命中或落空证据，不触发学习事件。
- 设置：已知键按载荷写入 `SettingsStore`；远端文档里没有的键，本机值保持不变（macOS 不用的设置不受影响）。
- 投影在每次合并之后与启动时各重建一次，以修复本机文件与同步状态的偏差。

### 6.6 体积与墓碑

- 墓碑（载荷为 `-` 的寄存器）永不按时间清理。理由：任意长时间离线、按时间丢墓碑、删除永不复活，三者不能同时成立；而保留墓碑的体积是可接受的。
- 估算：一个房间项明文约 75 字节（`f`、`b` 两个 25 字符寄存器加键与标点）。DEFLATE 之后，HLC 里重复的设备号与毫秒前缀被压掉，估计约 30 到 40 字节/项（S0 用生成器实测后把实测值写回本节）。
  - 典型用户（累计接触 300 个房间）：明文约 22 KB，压缩后约 10 KB，单次请求约 14 KB。
  - 重度用户（累计 2,000 个房间）：明文约 150 KB，压缩后约 70 KB。
- 硬上限：`rooms` 4,000 项、`veto` 1,000 项、`settings` 64 项、明文 1,048,576 字节、压缩后 196,000 字节。达到上限时拒绝新增键（已有键仍可改），提示「同步记录已满」。按估算，达到 4,000 个不同房间需要多年。
- 今后若要压缩墓碑（v3 起，v2 不实现），唯一安全的条件是：文档内维护设备名册与各设备已确认的版本，只清理 HLC 小于全体名册设备确认水位的墓碑，并写入永久的 `prunedThrough`；确认水位低于 `prunedThrough` 的设备必须按「加入」流程重来（远端为准），不得以旧快照合并。

## 7. 合并（纯函数，三端逐位一致）

### 7.1 规则

`merge(A, B)`：
- `schema`：取较大值。
- 两边都是对象：键取并集，同键递归合并。
- 两边都是字符串：取 UTF-8 字节序较大者。
- 一边缺：取另一边。
- 类型不一致（字符串对对象等）：该文档非法（第 7.3 节）。

合并只看结构，不理解业务含义。互斥、顺序、上限都在投影里处理，不写回文档。

### 7.2 性质（测试必须覆盖）

- 字节序是全序，字符串相等当且仅当字节相等，所以每个叶子上的 max 是半格；键并集与逐键递归保持半格。于是 `merge` 满足交换律、结合律、幂等，对三输入的任意分组结果相同。
- 未知字段只要是字符串叶子就按同一规则保留，旧客户端转一圈不会删掉新字段。
- 投影是文档的纯函数，同一文档在三端得到相同的收藏顺序、屏蔽集合与「不想看」集合。

### 7.3 合法性（不满足就整份拒收：不合并、不推送、保留本地，界面提示）

- 顶层是对象；`schema` 为整数。大于 2 时不算非法，进入只读：既不合并也不推送，提示「请更新 App」。
- `rooms` 的键与字段格式符合第 6.3 节与第 6.2 节；`f`、`b`、`veto` 的值匹配 `^[0-9a-f]{24}[+-]$`；`n` 的载荷符合第 6.2 节；已知设置的载荷为 `0` 或 `1`；未知设置的载荷不超过 256 字节。
- 所有 HLC 的设备号不为 0、`l` ≥ 1，且满足第 5 节的 366 天界限。
- 未知顶层键与未知子字段只允许对象与字符串，嵌套不超过 4 层。
- 条目数与字节数不超过第 6.6 节上限。
- 写入方永不输出重复键。读取方的解析器能发现重复键时（安卓 `org.json` 会抛错）按非法处理；Swift `JSONSerialization` 发现不了，接受这个差异，因为能写入文档的只有持有 `K` 的己方设备。

## 8. 加密封装（写死）

- 明文流水线：文档 JSON（UTF-8，无 BOM，不要求键序或空白一致）→ raw DEFLATE（RFC 1951，无 zlib 头尾）→ AES-256-GCM。
  - Apple 用 `Compression` 框架的 `COMPRESSION_ZLIB`（即 raw DEFLATE）；安卓用 `Deflater(level, true)` 与 `Inflater(true)`（按 JDK 文档，nowrap 模式在输入末尾补一个 0 字节）。
  - 解压时流式计数，超过 1,048,576 字节立即中止并按非法处理（防解压炸弹）。
  - 各端压缩输出不要求逐字节相同。金样本固定的是压缩后的字节，详见第 17 节。
- 信封 = ASCII `e1.` + base64url(nonce) + `.` + base64url(ciphertext ‖ tag)。
  - nonce：12 字节，每次封装由系统 CSPRNG 新生成；随机源报错即中止。
  - tag：16 字节。
  - AAD = ASCII `vela-sync/e1|` + blobID（64 个小写 hex）+ `|` + 该信封将要存放的版本号（第 4.2 节十进制）。例：版本 7 的 AAD 是 `vela-sync/e1|<64hex>|7`。把版本绑进 AAD，服务端就无法把旧密文贴上新版本号。
- Apple：`AES.GCM.seal(plain, using: SymmetricKey(data: encKey), nonce: AES.GCM.Nonce(data: nonce), authenticating: aad)`，取 `.ciphertext` 与 `.tag` 拼接；不用 `.combined`（它含 nonce）。解封用 `AES.GCM.SealedBox(nonce:ciphertext:tag:)`。
- 安卓：`Cipher.getInstance("AES/GCM/NoPadding")`，`GCMParameterSpec(128, nonce)`，`updateAAD(aad)`；`doFinal` 输出本来就是 ciphertext ‖ tag。
- 网络重试（同一 base 的同一请求）原样重发同一个信封；凡是重新合并（如 409 之后），一律重新封装并换新 nonce。
- nonce 碰撞概率约为 q²/2^97（q 为同一 `encKey` 下的累计加密次数，含失败重试）。三台设备十年约 10^6 次，概率约 6e-18，可以忽略。不得改成计数器 nonce，因为多台设备共用 `encKey`，计数器会重复。
- 尺寸：压缩后不超过 196,000 字节，信封不超过 262,144 字节，请求体不超过 266,240 字节。客户端在封装前检查，超限不发送并提示。

## 9. 写入认证（写死）

- 每次写操作都用 `signSeed` 签名（RFC 8032 纯 Ed25519，无预哈希、无上下文）。签名 64 字节，传输时用 base64url（86 个字符）；公钥用 base64url（43 个字符）。
- 被签消息 = 以下 5 行 ASCII，用 `0x0A` 连接，末尾不加换行：
  1. `vela-sync/v2/` + op，op ∈ `put` | `delete` | `retire`
  2. blobID
  3. base（请求所基于的当前版本，十进制）
  4. next = base + 1（十进制）
  5. put 时为小写 hex(SHA-256(信封的 ASCII 字节))；delete 与 retire 时为单个 `-`
- 服务端用该行登记的 `pub` 验签。创建（base = 0）时请求体带 `pub`，服务端用它验签并登记。之后 `pub` 永不改变，删除与退役后也保留。
- 签名覆盖 blobID、base、next 与信封哈希，所以：
  - 重放：同一签名只在版本恰为 base 时有效，成功一次后版本已前进，再次提交得到 409。
  - 跨 blob 与改体：blobID 与信封哈希都在签名里。
  - ABA：版本号永不回退、永不复用（删除与退役也让版本加一并保留行），同一 `(blobID, next)` 至多被接受一次。
  - 删除复活：删除后的行状态为 `deleted`，此后的 put 与创建一律 410。持旧码的设备也无法重建。
- 抢注：只有在创建请求途中能看到并拦截请求的一方（Cloudflare、服务端本身）才可能抢先用自己的公钥创建，此前 blobID 不出现在任何地方。客户端每次 GET 后核对返回的 `pub` 等于本机派生的 `pub`（安卓若求不出公钥，就用 `signSeed` 签一条固定消息，再用返回的 `pub` 验签代替核对）。不一致即报「同步空间被占用，请换码」，不写入。这一残余风险属于在途方的可用性攻击，接受。
- 未采纳「blobID = H(pub)」（它能从根上排除抢注），原因是那样一来每台设备都必须能从种子求出公钥，而安卓这一路径尚未验证。S4 探针若证明可行，v2 定稿前可以改用。
- 签名只证明「持码者写的」，挡不住服务端删除、隐瞒或回滚数据。这些由第 11.4 节的回滚检测与用户本机数据兜底。

## 10. 服务端

### 10.1 接口（所有响应 `Content-Type: application/json`、`Cache-Control: no-store`，JSON 响应都带 `now` 毫秒）

| 请求 | 成功 | 失败 |
|---|---|---|
| `GET /v2/blob/{id}` | `200 {"ver":n,"pub":"…","data":"<信封>","sig":"…","now":…}` | `404` 不存在；`410 {"ver":n,"state":"deleted"|"retired","now":…}` |
| `PUT /v2/blob/{id}`，体 `{"base":n,"data":"…","sig":"…","pub":"…"}`（`pub` 仅 `base=0` 时必带，其余时候不得带） | `200 {"ver":n+1,"now":…}` | `409 {"ver":当前,"pub":…,"data":当前,"sig":…,"now":…}`；`403` 验签失败；`404` 行不存在且 base≠0；`410` 已删除或退役；`413`；`429` |
| `POST /v2/blob/{id}/delete`，体 `{"base":n,"sig":"…"}` | `200 {"ver":n+1,"now":…}`，行变为 `deleted` | 同上 |
| `POST /v2/blob/{id}/retire`，体 `{"base":n,"sig":"…"}` | `200 {"ver":n+1,"now":…}`，行变为 `retired` | 同上 |

- `id` 必须匹配 `^[0-9a-f]{64}$`，否则 400。`base` 与 `ver` 为 0 到 2^53−1 的整数。信封须匹配 `^e1\.[A-Za-z0-9_-]{16}\.[A-Za-z0-9_-]{22,}$` 且不超过 262,144 字节。
- 版本不放在 `If-Match` 头里，而是放在请求体，避免中间代理改写条件头。
- 没有列表、枚举、搜索接口。未知路径一律 404。

### 10.2 存储与原子性

- SQLite（WAL，`synchronous=FULL`，`busy_timeout` 5 秒），单表：
  `blobs(id TEXT PRIMARY KEY CHECK(length(id)=64), state TEXT NOT NULL CHECK(state IN ('live','deleted','retired')), ver INTEGER NOT NULL, pub BLOB NOT NULL CHECK(length(pub)=32), data TEXT, sig BLOB, created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL)`。
- 每个写请求在一个 `BEGIN IMMEDIATE` 事务里完成：读行 → 验签 → 状态与版本检查 → `UPDATE … WHERE id=? AND ver=? AND state='live'`，影响行数必须为 1，否则回滚并返回 409（附同一事务里读到的已提交数据）→ COMMIT。创建用 `INSERT`；主键冲突时回滚，返回 409 与当前行。
- 已存在的行收到 `base=0` 返回 409；不存在的行收到 `base≠0` 返回 404，不创建。
- 删除与退役：`data` 置空，`sig` 置空，`ver` 加一，`pub` 保留，行不删除。

### 10.3 来源、限流与配额

- 进程只监听 `127.0.0.1`，cloudflared 在同机转发；主机上没有其他通向该端口的转发（部署验收要核查）。
- 只信任 `CF-Connecting-IP`：缺失、重复或不是合法 IPv4/IPv6 时返回 400；忽略 `X-Forwarded-For` 等其他头。IPv6 按 /64 聚合计数，IPv4 按单个地址计数。
- 限额（超出返回 429 与 `Retry-After` 秒数）：
  - 每个 IP：所有请求每分钟 120 次；创建每小时 5 次；验签失败每分钟 5 次。
  - 每个 blob：成功写入每分钟 30 次。验签失败不计入该 blob 的额度，免得攻击者耗尽受害者的写额度。
  - 全局：写入每分钟 600 次；创建每天 200 次；总行数 10,000；数据总量 512 MB。达到行数或总量上限时拒绝创建（507），已有空间照常读写。
  - 限流器状态在内存中，按 LRU 最多保留 10,000 个 IP，超时 1 小时淘汰。
- HTTP 资源：头部总长不超过 8 KiB；写请求必须带 `Content-Length`（缺失返回 411），不接受 `Transfer-Encoding`（返回 400）；先检查长度，超过 266,240 字节直接 413、不读体；读取超时 10 秒；并发连接上限 32。

### 10.4 日志、缓存与备份

- 改写访问日志：只记时间、方法、路由模板（`/v2/blob/:id`）、id 前 8 位、状态码、体积档位、IP 前缀（IPv4 /24，IPv6 /48）。不记请求头、请求体、签名、公钥、完整 id。journald 保留 14 天。
- Cloudflare：该主机名设置缓存规则「绕过缓存」，不开日志推送。Cloudflare 边缘本身看得到完整路径与请求体，我们控制不了，威胁模型按它可见处理。
- 备份：每日用 `sqlite3.Connection.backup()` 生成一致性快照，文件权限 0600，目录仅 root 可读，保留 7 天。内容只有密文、公钥、签名、版本与状态。
- 删除与退役事件追加写入 `tombstones.log`（完整 id、新版本、时间；0600）。恢复备份时先恢复快照，再重放快照时间之后的 `tombstones.log` 条目，保证删除不会因恢复而复活。恢复演练写进 RUNBOOK（S5）。
- 恢复备份即一次服务端回滚。客户端按第 11.4 节检测与修复，数据不丢，因为每台设备本地都有完整的同步状态。

### 10.5 实现约束

- Python 3 标准库：`http.server.ThreadingHTTPServer`、`sqlite3`、`hashlib`、`hmac`、`json`。标准库没有 Ed25519，验签用仓库内自带的 RFC 8032 §6 参考实现改写的纯 Python 验证函数（只做验证，处理的都是公开数据，计时侧信道无关）。它必须严格执行：拒绝 S ≥ L；拒绝 R 与 A 的非规范编码与不在曲线上的点；用无余因子方程 [S]B = R + [k]A。须通过 RFC 8032 测试向量与 Wycheproof 的 Ed25519 向量。替代方案见第 19 节。
- systemd：`NoNewPrivileges`、`ProtectSystem=strict`、`ReadWritePaths` 只到数据目录、`MemoryMax=128M`、专用用户。

## 11. 客户端同步流程

### 11.1 本地同步状态（同步开启期间的唯一事实来源）

- 文件 `sync-state.json`（与 `feed-curation.json` 同目录）：文档、HLC `(l, c, dev)`、`gen`（本地操作计数）、`pushedGen`、`lastSeenVer`、`lastSeenHash`（最近确认的信封 SHA-256）、origin、blobID 前缀、迁移标记、换码状态、最近成功与失败信息。
- 该文件排除出备份（Apple 设 `isExcludedFromBackup`，安卓写进备份排除规则）。设备号放在钥匙串（第 13 节），随 `K` 一起不进备份，这样备份恢复到另一台机器时不会克隆出同一设备号。
- 读写沿用 `PreferenceQuarantine` 口径：读失败就把坏文件改名备份，同步进入「暂停：同步状态损坏」，不推送，提供「重新加入」（按加入流程，远端为准）。改名也失败时只读，同样暂停。空读永不解释为「用户删光了」。
- 写顺序：用户操作 → 内存中文档写入寄存器、`gen` 加一 → 同步写 `sync-state.json`（原子替换，几 KB，主线程外的串行队列，完成后才确认操作）→ 由投影派生 `Curation` 与 `Taste` 的变化，按现有方式保存。`sync-state.json` 写失败时，本次操作在内存中仍生效，界面提示「保存失败」，下次操作时重试；这次操作不会被当作已同步。
- 启动时若同步开启：先读同步状态，再用投影覆盖本机收藏与「不想看」，修复两份文件的偏差。

### 11.2 协调器（每个空间一个，串行）

一次同步周期：
1. GET。
2. 校验并解密（AAD 用响应里的 `ver`），检查 `pub`，做回滚检测（第 11.4 节）。
3. `L = merge(L当前, R)`。注意合并的是此刻内存里的当前状态，而不是发起请求时的快照，所以请求期间新增的改动不会丢。随后推进 HLC，保存状态，有变化时更新投影。
4. `L` 与 `R` 语义相等且 `gen == pushedGen` 时结束（不做无意义的 PUT）。
5. 否则记下 `sentGen = gen`，以 `next = ver + 1` 封装并签名，PUT `base = ver`。
6. 200：`lastSeenVer = ver + 1`，`lastSeenHash` = 本次信封哈希，`pushedGen = max(pushedGen, sentGen)`。请求期间产生的新操作让 `gen > pushedGen`，留到下一周期。
7. 409：用响应体回到第 2 步。一个周期最多重试 3 次，超过就退避，`gen > pushedGen` 保留，不丢任何东西。
8. 超时或连接中断：结果未知，不改 `pushedGen`。下一周期 GET 时若 `ver == 发出的 next` 且信封哈希等于本机发出的那份，确认为已推送。

### 11.3 触发时机（无轮询、无常驻连接）

- 启动、回到前台：一个周期。
- 本地操作：去抖 5 秒后一个周期；同一设备两次 PUT 间隔至少 10 秒。
- 打开收藏面板、口味面板、同步设置页：距上次成功 GET 超过 60 秒才发一个周期。
- 进后台或退出：`gen > pushedGen` 时尽力推一次（iOS 用 `beginBackgroundTask`，macOS 在退出流程里最多等 3 秒），不保证完成；未完成的下次启动会补推。
- 设置页「立即同步」。
- 失败退避：30 秒起翻倍，最长 1 小时；429 按 `Retry-After`。退避期内的触发直接跳过。

### 11.4 错误分类（失败可见、不打扰）

| 情况 | 处理 |
|---|---|
| 断网、超时、5xx、非 JSON 或截断的响应（如中间页的 HTML） | 暂时故障：退避后重试，不停用、不弹窗 |
| 429 | 按 `Retry-After` |
| 403 | 「云端拒绝了这台设备的写入」：停止自动写，保留一切，提示检查同步码或换码 |
| 404，且本机 `lastSeenVer > 0` | 「云端空间不见了」：停止自动写，提供「用本机数据重建」（以 base=0 创建，同一公钥）；不自动重建 |
| 410 deleted / retired | 停止同步，保留本地数据与同步状态；deleted 提示「云端数据已被清除」，retired 提示「已更换同步码，请输入新码」 |
| 413、本机超出体积上限 | 「同步数据过大」，停止推送 |
| 未知信封前缀、schema 更大 | 只读，提示更新 App |
| 文档非法（第 7.3 节） | 不合并、不推送，提示，保留现场 |
| AEAD 解封失败 | 下次触发重试一次；连续两次（不同周期）失败才暂停，保留 `K`、本地数据与 `gen` |
| `pub` 与本机派生不一致 | 「同步空间被占用」：停止写入，建议换码 |
| 回滚：`ver < lastSeenVer`，或 `ver == lastSeenVer` 但信封哈希不同 | 合并照做（合并不会让本机丢数据），暂停自动推送，提示「云端数据比本机记录的旧（服务器可能恢复了备份）」，提供「用本机数据修复」：确认后按正常周期推送，并把 `lastSeenVer` 重置为服务端的值 |
| 本机时间与服务端相差超过 24 小时 | 暂停写入，提示校准时间 |

- 设置页显示：上次成功同步时间、是否有待同步的改动、最近一次失败的类别。除加入确认、410、换码、「空间被占用」以外不弹窗。
- 新设备首次加入时如果服务端正处于回滚状态，它无从察觉，只会先拿到较旧的状态。等其他设备推送后会补齐，不会丢失。

## 12. 开启、加入、关闭、清除、换码

### 12.1 创建（「在这台设备上开启同步」）

1. 说明页：将上传哪些数据、同步码等于全部权限、丢码不可恢复。用户同意后继续。
2. 生成 `K` 与设备号，存入钥匙串或 Keystore；派生 blobID、`pub`。
3. 迁移盖章（第 14.1 节，创建方全部盖章），写同步状态。
4. 创建（PUT base=0 带 `pub`）。409 说明行已存在（只有极小概率或被抢注），按加入流程的 `pub` 核对处理。
5. 显示同步码与短指纹，要求用户保存；提供复制（敏感标记）。

### 12.2 加入（「我已有同步码」）

1. 粘贴，按第 4.3 节严格解析；失败即报无效。
2. 确认页：显示主机名、短指纹，以及「将把本机的收藏、屏蔽、不想看与两个设置加密后上传到 <主机名>；持有这个同步码的人能看到并修改这些数据」。用户确认后继续。
3. GET：
   - 404：提示「这个同步码没有对应的已有空间」，提供「仍用此码创建」或取消。
   - 410：提示该空间已清除或已换码，不加入。
   - 200：核对 `pub`、解密、校验文档；任一失败按第 11.4 节报错，不保存 `K`。
4. 预览：「将上传 N 个收藏、M 个屏蔽、P 个不想看；本机有 X 项云端已有记录，以云端为准（其中 Y 项会从本机移除）」。用户确认。
5. 保存 `K`、新设备号，按第 14.1 节加入方规则盖章，合并，推送。

### 12.3 多台设备同时首次开启

- 同一个码同时加入（双方都 GET 到 404 再创建）：服务端主键冲突，一方 409，用响应合并后重试，结果是并集。
- 两台设备各点了「创建」，得到两把 `K`：两边永不相遇。引导页明确区分「创建」和「加入」，并提示「其他设备已开启过就选加入」。补救办法：在其中一台选「加入」另一台的码，本机原空间的同步状态按换码延续规则（第 12.5 节第 6 条）带入新空间，然后提示可删除原空间。

### 12.4 本机关闭、清除云端

- 本机关闭：删除本机的 `K`、设备号与同步状态，本地收藏与口味保留，其他设备不受影响。这一步撤销不了这台设备曾拿到的码；要撤销请换码。
- 清除云端：二次确认，文案「将删除云端数据，所有设备停止同步；各设备本地数据保留」。签名 delete（base = `lastSeenVer`，409 就用新版本重试）。成功后本机同关闭。其他设备收到 410 deleted 后停止，可以新建空间。被清除的空间不可重建，同一个码作废。
- 清除全部偏好（现有 `clearAllPreferences`）在同步开启时会写入 `veto` 的 `-`，文案改为「将在所有同步设备上取消『不想看』；收藏与屏蔽保留」。

### 12.5 换码（可恢复、能撤销旧写权限）

状态持久化在 `sync-state.json` 的 `rekey` 字段，每一步完成才进入下一步，崩溃后从当前步继续：

1. `syncingOld`：对旧空间跑同步周期直到 `gen == pushedGen`。
2. `prepared`：生成 `K'` 并存入钥匙串的 `K.next` 项，派生新 blobID 与 `pub'`。
3. `newCreated`：以当前文档创建新空间（base=0），然后 GET 新空间，确认能解密。
4. `oldRetired`：对旧空间发签名 retire（base = 旧 `lastSeenVer`）。遇到 409（其他旧设备刚写过）就拉取旧空间、合并、推到新空间，再重试 retire。成功后旧空间的数据被清空，持旧码者再也读写不了，也无法重建。
5. `done`：`K.next` 转正，删除旧 `K`，显示新码与新指纹。
6. 其他旧设备收到 410 retired 后停止，提示输入新码。用户输入新码后走加入流程，但本机已有、带 HLC 的同步状态原样带入（不按加入方规则重新盖章），所以它离线期间未上传的操作会进入新空间。
- 新码只经用户手动传递，不用旧 `K` 加密下发；否则泄露旧码的人也能拿到新码。
- 限制要写进文案：从未上线、也从未输入新码的设备，离线操作只留在本机。

## 13. 密钥存储

- Apple：通用密码项，service `com.vela.sync`（不用 `com.vela.stage`，因为 `LegacyLoginCleanup` 会清理那个 service 下的条目），account 为 `K`、`K.next`、`dev`。`kSecAttrAccessible = kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`，`kSecAttrSynchronizable = false`（显式），不设共享访问组。macOS 用 `kSecUseDataProtectionKeychain = true`。缺少钥匙串授权导致失败（`errSecMissingEntitlement`）的构建视为不支持同步，不退化成明文文件。
- 安卓：`AndroidKeyStore` 里的 AES-256-GCM 包裹密钥（别名 `vela_sync_wrap`），`setUserAuthenticationRequired(false)`，每次包裹用 Cipher 生成的随机 IV。包裹后的 `K` 与设备号存进专用 SharedPreferences 文件 `vela_sync`，该文件与 `sync-state.json` 都写进 `dataExtractionRules`（API 31 及以上）与 `fullBackupContent`（API 30 及以下）的排除项。
- 读取结果分三类，处理不同：
  - 不存在：未开启。
  - 暂时不可用（设备首次解锁前，`errSecInteractionNotAllowed`；Keystore 暂时性错误）：本次跳过同步，稍后再试。
  - 永久失效（Keystore 密钥丢失，`KeyPermanentlyInvalidatedException`，解包失败）：提示「同步密钥丢失，请重新输入同步码」。
- 任何失败都不得自动生成新 `K`。恢复只靠用户保存的同步码。

## 14. 迁移与升级

### 14.1 首次开启时给已有本地数据盖章（每个空间只做一次，迁移标记存在同步状态里）

- 数据源：`Curation` 的收藏与屏蔽数组、`Taste` 中 `vetoed == true` 的 `t:` 与 `g:` 键、`SettingsStore` 中 `defaults.object(forKey:) != nil` 的 `publicOnly` 与 `infoAlwaysOn`（未设置过的缺省值不盖章，免得用缺省值覆盖别的设备的明确选择）。
- 读取处于失败、只读或隔离状态的 store 不参与：开启或加入前先检查 `isReadOnly` 与读取结果，不正常就拒绝开启并提示。
- 盖章顺序：收藏数组从末尾往前逐个 tick，使原数组第一个（最新）得到最大 HLC，投影顺序与原来一致；屏蔽同理；`veto` 按键的 UTF-8 升序；设置按键名升序。迁移只写对应的 `+` 寄存器（以及需要时的 `n`），不写成对的 `-`。创建方没有远端；加入方只给远端没有记录的键盖章，所以不存在需要压过的远端寄存器。
- 创建方：全部盖章。
- 加入方：只给远端完全没有该键的项盖章；远端有该键（无论 `+` 或 `-`）就以远端为准，本机按投影调整，第 12.2 节第 4 步已向用户预览。不提供逐项选择，以保持轻量（第 19 节待裁决）。
- 换码延续或切换空间的设备：已有 HLC 的寄存器原样带入，不重新盖章。
- 幂等：迁移标记防止重复盖章；导入收藏文件只对此刻不在收藏中的名字产生写入，重复导入同一文件不产生新寄存器。

### 14.2 升级与降级

- 同一 schema 主版本内的新字段只能是字符串叶子寄存器，旧客户端用通用合并原样保留。禁止用 Codable 把文档解码成已知结构体再编码（会丢未知字段）：文档在内存中保持通用 JSON 树，已知字段通过访问器读写。
- schema 主版本升级：新客户端写出更大的 `schema`，旧客户端进入只读并提示更新。新客户端在写出更大的 `schema` 之前，应先看到全部已知设备都已支持（v3 的设备名册提供这项信息；v2 没有名册，所以 v2 之内不升主版本）。
- 封装版本升级：新客户端能读 `e1` 与新版本，在确认全部设备支持之前继续写 `e1`。
- 派生代升级（`vela3`）：只能经换码流程迁到新空间。
- 降级（用户装回旧版本）：旧版本遇到更新的 schema 或封装就只读，不覆盖。

## 15. 威胁模型

| 参与方 | 能看到 | 能做 | 不能做 | 对策与残余 |
|---|---|---|---|---|
| Cloudflare 边缘（TLS 在此终结） | 完整路径（含 blobID）、请求头与体（密文、签名、公钥）、IP、时间、体积 | 丢弃、延迟、重放、回送旧响应；在创建请求途中抢先注册 | 解密；伪造或篡改写入；把旧密文贴上新版本号 | 签名（第 9 节）、AAD 绑版本（第 8 节）、回滚检测（第 11.4 节）；抢注与拒绝服务是残余，可被察觉 |
| 服务端或其运维、被入侵的服务器 | 同上，加上数据库与备份 | 删除、隐瞒、回滚、对不同设备给出不同版本 | 解密；伪造写入 | 同上；每台设备本地有完整同步状态，可以修复云端 |
| 被动网络观察者 | TLS 元数据、访问时间、体积 | 无 | 内容 | TLS |
| 持有同步码者 | 全部同步数据 | 读、改、删空间 | 读本机未同步的口味学习数据 | 等同于「把手机交给别人」；撤销靠换码 |
| 诱导粘贴恶意同步码（攻击者控制的主机与 `K`） | 用户确认上传后的数据 | 解密该用户上传的数据 | 用户不确认就拿不到 | 确认页显示主机名与上传说明（第 12.2 节） |
| 丢失或被盗的设备 | 本机数据与 `K` | 以持码者身份读写 | 换码后继续读写 | 换码（第 12.5 节） |
| 备份泄露（iCloud、安卓备份、服务端快照） | 服务端快照：密文与元数据 | 无 | 解密（`K` 不进任何备份） | 钥匙串与 Keystore 属性、备份排除规则 |
| 滥用存储的匿名者 | 无 | 创建大量空间、灌请求 | 突破全局配额 | 第 10.3 节限流与配额 |

- 元数据泄露：密文体积大致反映收藏与屏蔽的数量，访问时间反映使用时段。接受。
- 前 8 位 id 是可关联标识，不是匿名化；只用于排错，保留 14 天。

## 16. 隐私说明文案要点（开启与加入时展示，设置页可再看）

- 同步的内容：收藏、屏蔽、「不想看」的标签与性别、两个显示设置；不同步观看记录与学习数据。
- 内容在本机加密后才上传；服务器与网络运营方（Cloudflare）看不到内容，但能看到访问时间、大致数据量，并且有能力删除数据或让同步暂时失败。
- 同步码就是钥匙：谁拿到谁就能看到和修改全部同步数据。不要截图分享，不要发给别人。
- 丢了同步码、又没有任何一台已加入的设备，数据无法找回。
- 本机关闭同步不会撤销别人手里的码；要撤销，请用「更换同步码」，再在每台设备上输入新码。
- 「清除云端数据」会让所有设备停止同步，各设备本地数据保留；服务器备份中的密文最多再保留 7 天。
- 远端改动在下次打开 App、回到前台、打开收藏或口味面板，或点「立即同步」时出现。

## 17. 金样本 `Tests/Fixtures/sync/vectors.json`

由独立实现生成：S0 用 Go 标准库（`crypto/hkdf`、`crypto/aes`、`crypto/cipher`、`crypto/ed25519`、`crypto/sha256`、`compress/flate`）写生成器 `scripts/sync/vectors/`，不依赖三端任何代码。Go 的 Ed25519 签名是确定性的；CryptoKit 的签名带随机性，所以签名一律只做「验证对方的签名」与「自己签的能被验证」，不比字节。各段字段：

- `kdf[]`：`K_hex`、`salt_hex`、`info`（三条）、`blobID`、`encKey_hex`、`signSeed_hex`、`pub_b64url`、`fingerprint`。
- `base64url[]`：`bytes_hex`、`text`；`base64urlInvalid[]`：`text`、`reason`（带 `=`、含空白、非字母表、末位比特非零）。
- `code[]`：`code`、`K_hex`、`origin`、`checksum`；`codeInvalid[]`：`code`、`reason`（前缀错、42 或 44 字符、非规范末位、校验错、`http`、userinfo、路径、`/`、query、fragment、IP 字面量、大写主机、`:443`、非 ASCII 主机）。
- `deflate[]`：`deflated_b64url`、`inflated_utf8`；`deflateInvalid[]`：超过 1 MiB 的解压炸弹、截断流。
- `envelope[]`：`encKey_hex`、`blobID`、`ver`、`nonce_hex`、`plaintext_hex`（即压缩后的字节）、`aad_hex`、`envelope`（三端必须逐字节相同）；`envelopeInvalid[]`：改 tag、改 AAD 中的版本、截断、错误前缀、填充的 base64、nonce 长度不对。
- `sign[]`：`signSeed_hex`、`pub_b64url`、`op`、`blobID`、`base`、`next`、`envelope_sha256_hex`、`message_hex`、`sig_b64url`；`signInvalid[]`：S ≥ L、非规范 R、错消息、错公钥。
- `hlc[]`：`state`（l, c, dev）、`events[]`（`local` 加 `pt`，或 `receive` 加远端最大值）、每步 `expected`；覆盖回拨、同毫秒、计数溢出、24 小时与 366 天两个界限。
- `merge[]`：`a`、`b`、`c`、`expected`（三输入任意分组都等于它）；覆盖同 HLC 不同载荷、未知字段、未知顶层键、缺项；`mergeInvalid[]`：类型冲突、格式错、超上限、设备号为 0。
- `projection[]`：`doc`、`expected.favorites`（有序）、`expected.blocked`（有序）、`expected.vetoed`、`expected.settings`；覆盖互斥平局、超过 300、显示名、非 ASCII 标签。
- `ops[]`：初始 `doc`、HLC 状态、操作序列（第 6.4 节的函数名与参数）、期望 `doc`。
- `migration[]`：本地 `Curation`、vetoed 键、显式设置、可选的远端 `doc`、固定时钟、期望 `doc` 与预览计数。

## 19. 待用户裁决

1. 安卓 Ed25519 需要 API 33（Android 13）及以上，同步在更低版本上不可用；从种子求公钥的平台路径待 S4 探针。若探针失败，备选：(a) 安卓只能加入、不能创建（加入时用「签名再验签」核对 `pub`）；(b) 签名密钥改为创建方随机生成，私钥用 `encKey` 加密后存进文档，加入方从文档取得。
2. 设置只同步 `publicOnly`、`infoAlwaysOn`；`muted`、`phoneDual`、`pipAutoEnter` 不同步。
3. 服务端验签：自带纯 Python 验证（本稿默认）、引入 `cryptography` 包，或调用系统 `openssl` 子进程，三选一。
4. 加入时远端已有记录的键以远端为准（本机可能因此移除少量收藏），只给预览计数、不提供逐项选择。
5. 同步开启后，导入的收藏排在最前（按文件顺序），不再像现在那样接在已有收藏后面。
6. 重度用户的单次传输会到几十 KB（压缩后），超出「几 KB」的说法；典型用户约 10 KB。
7. 服务端恢复备份后，各设备需要用户点一次「用本机数据修复」，不自动推送。
8. S4 的 JVM 单测需要真实的 `org.json`（Android 单测里的是桩），拟以「仅测试」依赖引入同 API 的构件；产品依赖不变。
