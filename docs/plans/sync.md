# 跨设备同步（同步码 + 端到端加密）设计

> 状态：设计稿 v4（2026-11-18），实现契约。用户已批方案：不做账号，用同步码加端到端加密，服务端只存密文。v2、v3、v4 分别按三轮对抗审查修订，处置见第 20 到 22 节。编排者裁决：v4 起不再在纸面追求严格代数性质，改为「简化加测试证明」；本稿之后直接进入实现，不再做完整设计审查。
> 本文所有标注「写死」的地方是三端（Swift、Kotlin、服务端 Python）逐字节一致的契约，实现者不得自选。

## 0. 版本变化摘要

- v2：数据模型与现有代码同形（收藏与屏蔽成对记账、只同步「不想看」）；每项版本改用 HLC；写入改为 Ed25519 签名；同步状态成为开启期间的唯一事实来源；字节级格式写死。
- v3：删除换码与「恢复后继续用原空间」；服务端 `epoch`；容量对齐本机并引入裁剪函数 `E`；口味键加 NFC；离线快钟在发出前重新盖章；按空间计量配额；创建、加入、关闭、清除有持久化步骤；写入用户裁决。
- v4：
  - 删除空间后服务端保留不可复用的删除墓碑，删除后的任何写请求（包括重放的旧首写）一律 410（第 10.2 节）。
  - 删除「未知字段保留」：只接受本 schema 版本的文档，遇到更高版本只读并提示升级（第 3、7.3 节）。
  - 合并的承诺改为「确定性加最终一致」，由多副本随机模拟测试证明，不再声明裁剪后满足结合律（第 7.2 节）。裁剪全部写成带平局规则的全序。
  - 字节上限改为写入前实测：先裁最旧墓碑，仍超则拒写。上限按压缩前计量，压缩只作优化（第 6.7、8 节）。
  - 关闭、清除、加入前加投影落盘屏障（第 12.2 节）。
  - 「不想看」在同步与本机专用之间分配 500 的总额（第 6.6 节）；导入用固定窗口（第 6.4 节）；加入的恢复字段（第 12.4 节）；创建频率在数据库里计数（第 10.3 节）；安卓探针按能力分级（第 18 节 S0）；同步标签域限定 Unicode 13.0 的已分配 BMP 码点（第 6.3 节）。

## 1. 目标与边界

- 同步：收藏、屏蔽、口味里的「不想看」标签与性别、两个设置（`publicOnly`、`infoAlwaysOn`）。
- 不同步：命中与落空证据（hit/miss）、停留、最近看过（seen）、每日命中率、学习暂停开关、「不感兴趣」产生的落空、收藏带来的命中加权、手动加强的权重、观看账本、缩略图缓存、窗口与透明度类设置、音量、`muted`、`phoneDual`、`pipAutoEnter`。理由：量大、与设备相关，或远端改动会在本机产生意外后果（远端 `muted=false` 会让当前设备突然出声）。
- 不做：账号、找回、分享给他人、服务端可读的任何字段、实时推送、轮询、常驻连接、第三方依赖、自动换码。
- 平台门槛：macOS 14 与 iOS 17（与现有最低版本相同）；安卓 Android 13（API 33）及以上，且须通过 S0 探针的对应能力级别（第 18 节），才显示同步入口。更低的安卓版本照常使用 App，只是没有同步入口，也不为此引入第三方库。
- 可见延迟承诺：远端改动在本机「下次启动或回到前台、打开收藏或口味面板、点立即同步」时出现；两台设备都停在前台且没有上述动作时，不保证看到对方改动。这是「无轮询」的直接代价，写进隐私与帮助文案。
- 服务端地址不进公开仓：Apple 端经本地、不入库的 xcconfig 注入，安卓经本地 gradle 属性注入，同步码里也带地址。构建分两种情况：
  - 构建未启用同步功能（编译开关关）：完全没有同步入口。
  - 启用了同步功能但没有默认地址：隐藏「创建」，保留「加入」，地址只从同步码取。主机名不保密，不当访问控制。

## 3. 版本号体系（四个互相独立）

| 名称 | 现值 | 出现在 | 改变它意味着 |
|---|---|---|---|
| 同步码格式与密钥派生代 | `vela2` | 同步码前缀、HKDF info | 同一个 `K` 会派生出不同空间：只能由用户关闭再以新码重开 |
| 封装版本 | `e1` | 信封前缀、AAD | 新算法；旧客户端遇到未知前缀进入只读 |
| 文档 schema | `2` | 明文 `schema` 字段 | 任何结构变化都升这个号；旧客户端遇到更大值进入只读并提示升级 |
| 服务端 API | `/v2` | 路径 | 旧路径保留到所有客户端升级 |

- 文档只有一种合法形状（第 6.1 节），不预留未知字段。客户端只接受 `schema == 2`：更大值进入只读（不合并、不推送），提示「其他设备的 App 更新，请更新本机 App」；更小值或其他形状一律非法。
- 代价：将来升 schema 时，没有升级的设备停止同步，直到升级。个人少量设备可以接受，比在每个版本里维护未知字段的合并规则简单得多。

## 4. 密钥、派生与同步码（写死）

### 4.1 主密钥与派生

- `K`：32 字节，由系统 CSPRNG 生成（Apple `SecRandomCopyBytes`，安卓 `SecureRandom`）。随机源报错即中止，不得退化。
- HKDF-SHA256（RFC 5869），三次独立调用，参数相同：IKM = `K`；salt = 32 个 `0x00` 字节（显式传入，不传空 salt）；L = 32。
  - `blobID` = 小写 hex(HKDF(info = ASCII `vela-sync/v2/id`))，64 个字符。
  - `encKey` = HKDF(info = ASCII `vela-sync/v2/enc`)，AES-256-GCM 密钥。
  - `signSeed` = HKDF(info = ASCII `vela-sync/v2/sign`)，RFC 8032 Ed25519 私钥种子。
- 安卓手写 HKDF：PRK = HMAC-SHA256(key = salt, data = K)；OKM = HMAC-SHA256(key = PRK, data = info ‖ `0x01`)。L = 32 只需一个块。
- Apple：`HKDF<SHA256>.deriveKey(inputKeyMaterial: SymmetricKey(data: K), salt: Data(count: 32), info: Data(info.utf8), outputByteCount: 32)`。
- 公钥 `pub` = RFC 8032 编码的 32 字节 Ed25519 公钥。Apple：`Curve25519.Signing.PrivateKey(rawRepresentation: signSeed).publicKey.rawRepresentation`。安卓：私钥用 PKCS#8 DER 前缀 `302e020100300506032b657004220420` 加种子，经 `KeyFactory.getInstance("Ed25519")` 导入；公钥的取得方式由 S0 探针确定。
- 公钥核对消息（安卓取不到公钥时用来代替直接比较，写死）：ASCII `vela-sync/v2/pubcheck` + `0x0A` + blobID。用 `signSeed` 签名，再用服务端返回的 `pub` 验签；通过即视为一致。
- 短指纹 = `blobID` 前 8 个 hex 转大写，按 4-4 用 `-` 连接（例 `3F9A-0C21`）。两台设备对码用；它不是秘密，日志也只记这一段。

### 4.2 编码规则

- base64url：RFC 4648 §5 字母表，不补 `=`。解码器拒绝 `=`、空白、字母表外字符，以及末位未用比特不为 0 的非规范编码（实现：解码后重新编码必须与输入逐字节相等）。
- hex：一律小写；解析时拒绝大写。
- 十进制整数：无前导零（`0` 本身除外）、无正负号、无小数与指数，范围 0 到 2^53−1。

### 4.3 同步码

- 格式：`vela2:` + k43 + `.` + c6 + `@` + origin。
  - k43 = base64url(`K`)，必须正好 43 个字符，解码必须正好 32 字节。
  - c6 = 小写 hex(SHA-256(ASCII(`vela2:` + k43 + `@` + origin)) 的前 3 字节)，用于发现抄错、截断、改主机名。
  - origin 必须规范：`https://` + host + 可选 `:` + port。host 为小写 ASCII 的 DNS 名：每个标签 1 到 63 个字符，只含 `a-z0-9-`，不以 `-` 开头或结尾，至少两个标签，总长不超过 253。拒绝 IP 字面量、非 ASCII（国际化域名须为 punycode）、userinfo、路径（含单独的 `/`）、query、fragment。端口为 1 到 65535 的规范十进制，`:443` 视为非规范，拒绝。
- 解析任一条不满足即报「同步码无效」，不尝试修正（修正会把一位之差变成另一把合法密钥）。
- 请求地址 = origin + `/v2/...`。客户端不跟随任何重定向（3xx 当错误），不带 cookie，不用 URL 缓存，User-Agent 固定为 `Vela-Sync/2`。
- 完整同步码只允许出现在三个专用界面：创建后的「保存你的同步码」页、设置里需要再次验证身份（设备密码或生物识别）才能打开的「查看同步码」页、「加入」页的输入框。其他界面只显示短指纹。日志、崩溃报告、诊断信息里禁止出现整段同步码、`K` 或完整 `blobID`。
- 复制时标记敏感：iOS `UIPasteboard` 设 `localOnly` 与 120 秒 `expirationDate`；macOS 同时写 `org.nspasteboard.ConcealedType`；安卓设 `EXTRA_IS_SENSITIVE`。
- 二维码内容与文本相同，是可选项，只出现在上面两个专用展示页。

## 5. 混合逻辑时钟（HLC，写死）

### 5.1 表示与推进

- 每台设备在每个同步空间里持久化 `(l, c, dev)`：`l` 为毫秒（48 位）、`c` 为计数（16 位）、`dev` 为加入该空间时随机生成的 32 位设备号（`0x00000000` 保留不用）。
- 线格式：24 个小写 hex = 12 位 `l` + 4 位 `c` + 8 位 `dev`。三段定宽，所以字符串字节序等于元组 `(l, c, dev)` 的字典序。
- 本地事件（一次用户操作取一个 tick，同一操作写的多个寄存器共用这个值）：`pt` = 本机墙钟毫秒；`pt > l` 时 `(l, c) = (pt, 0)`；否则 `c < 0xFFFF` 时 `c += 1`；否则 `(l, c) = (l + 1, 0)`。新值先随同步状态落盘，再用于寄存器。
- 收到远端文档（已通过校验）：取其中所有寄存器 HLC 的最大 `(l', c')`；若 `(l', c') > (l, c)` 则令 `(l, c) = (l', c')`。收到时不 tick。由此，看见远端操作之后的本地操作必然排在它之后。
- 时钟回拨：`l` 已持久化，墙钟回拨时走「计数加一」分支，不会生成更小的时间戳。同一毫秒内连续操作靠 `c` 分出先后，先删后加不会丢。
- 静态合法界限（与接收方当前时间无关）：`1 ≤ l ≤ 0xFFFF00000000`，`dev ≠ 0`。不满足即文档非法。

### 5.2 限制快钟毒化

1. **在线时停写**：服务端每个 JSON 响应带 `now`（服务端毫秒）。本机墙钟与 `now` 相差超过 1 小时，暂停一切写入，提示「本机时间不准，校准后再同步」。
2. **离线时间戳在发出前重新盖章**：
   - 同步状态持久化 `maxSentL`：本机曾经发出过的任何 PUT（包括结果未知的）所含寄存器的最大 `l`。
   - 每次准备 PUT 时，以本周期 GET 得到的服务端时间 `N` 为准，找出候选集 `R` = 本机设备号写的、`l > N + 3,600,000` 的寄存器。
   - 若 `R` 非空且 `R` 中每个寄存器都满足 `l > maxSentL`（即从未离开本机）：把本机时钟重置为「文档中不属于 `R` 的寄存器的最大 HLC」与 `(N, 0)` 两者中较大的一个，然后按原 HLC 升序逐组重新 tick（原 HLC 相同的寄存器属于同一次操作，共用一个新 tick），载荷不变。
   - 若 `R` 中有寄存器已发出过（`l ≤ maxSentL`），这些寄存器不得改写。其余照常推进，诊断页记一条。
3. **结果**：诚实客户端传播出去的寄存器的 `l` 不超过推送时服务端时间加 1 小时，毒化的上限是约 1 小时的领先，而且只作用于与它并发、尚未看见它的操作。
- 不采纳「接收超前值时只推进计数、不推进物理部分」：HLC 按 `(l, c)` 字典序比较，只推进计数的话，看见远端未来时间戳之后的本地操作仍然小于它，「先看见、后操作」的删除就会输给它。
- 重新盖章只改写从未离开本机的寄存器，效果等同于用户在那一刻才做这些操作；合并本身是文档的确定性函数，与时钟无关。S1 的模拟测试包含快钟设备（第 7.2 节）。

### 5.3 设备号

设备号只要求在一个空间内唯一：10 台设备的碰撞概率约 1e-8。碰撞时最坏结果是同一 HLC 上出现两种取值，由第 6.2 节的平局规则确定性裁决。设备号与 `K` 一起存在钥匙串或 Keystore 里，不进备份。

## 6. 同步文档（加密前的明文）

### 6.1 结构（唯一合法形状）

```json
{
  "schema": 2,
  "rooms": {
    "alice":   { "f": "0193b2c4d5e60000a1b2c3d4+", "b": "0193b2c4d5e60000a1b2c3d4-", "n": "0193b2c4d5e60000a1b2c3d4Alice" },
    "bob_x":   { "b": "0193b2c4d5e70001a1b2c3d4+" }
  },
  "veto": {
    "t:asian": "0193b2c4d5e80000a1b2c3d4+",
    "g:m":     "0193b2c4d5e90000a1b2c3d4-"
  },
  "settings": {
    "publicOnly": "0193b2c4d5ea0000a1b2c3d41"
  }
}
```

- 顶层恰好有 `schema`、`rooms`、`veto`、`settings` 四个键，都必须出现（空对象写 `{}`）。
- 房间条目只能有 `f`、`b`、`n` 三个可选字段，至少有一个。
- `settings` 只能有 `publicOnly`、`infoAlwaysOn` 两个可选键。
- 出现任何其他键，文档非法（第 7.3 节）。

### 6.2 寄存器

- 所有寄存器都是字符串 = 24 位 HLC + 载荷。合并时取 UTF-8 字节序较大者。HLC 在前，所以先比时间，时间相同才比载荷。
- `rooms.<键>.f`（收藏）与 `.b`（屏蔽）：载荷 `+`（在）或 `-`（不在）。同一 HLC 上 `-`（0x2D）大于 `+`（0x2B），即同刻删除胜。
- `rooms.<键>.n`（显示用大小写）：载荷匹配 `^[A-Za-z0-9_]{2,30}$`，且按 ASCII 转小写后等于键的用户名部分（冒号之后）。
- `veto.<键>`：载荷 `+`（不想看）或 `-`（已撤销）。
- `settings.<键>`：载荷为 `1` 或 `0`（同刻 `1` 胜）。
- 缺失的寄存器等价于「HLC 全 0、载荷 `-`」，参与比较时小于任何真实寄存器。
- 寄存器比较、键的身份、文档相等，一律按 UTF-8 字节判断，不用平台的字符串判等（Swift `String ==` 按规范等价）。第 6.3 节保证所有键都是 NFC，所以 Swift 用 `String` 作字典键时，字节身份与 `String` 身份一致。

### 6.3 键规则

- 房间键（2026-11-18 用户裁决：预留多站点）：`<站点>:<用户名>`。站点标识匹配 `^[a-z][a-z0-9]{1,7}$`，v1 只有 `cb`（Chaturbate）合法，下一个计划接入的是 `c4`（Cam4）；用户名部分为 `Curation.key`（去首尾空白、小写）的结果，`cb` 下必须匹配 `^[a-z0-9_]{2,30}$`（与 `Room.isValidUsername` 同一字符集与长度）。整个键匹配 `^[a-z][a-z0-9]{1,7}:[a-z0-9_]{2,30}$`。本机现有无前缀的名字在开启同步与导入时一律映射为 `cb:` 前缀；投影回本机时 `cb:` 键去前缀写回现有 `Curation`（本机多站点改造另行完成后再改为带前缀存储）。接收到本端不认识的站点前缀：保留在同步文档里参与合并与裁剪，但不投影到本机。不合规的本机旧名字不进同步（第 14.1 节）。
- 性别键：`g:` + `f|m|t|c`（`Gender` 的 rawValue）。
- 标签键：只同步落在「同步标签域」里的标签，域外的「不想看」只留在本机。写死：
  1. 原始标签 `r`（站点给的字符串，不去首尾空白、不去 `#`，与 `Taste.tagKey` 一致）的每个码点都必须满足：在 BMP 内（≤ U+FFFF）；不是代理、私用区（U+E000 到 U+F8FF）或非字符；在 Unicode 13.0 中已分配（Swift `Unicode.Scalar.Properties.age` 不为空且不晚于 13.0；安卓 `android.icu.lang.UCharacter.getAge(cp)` 不晚于 13.0）；不是 White_Space、控制字符（Cc）、`"` 或 `\`。
  2. `r` 的码点数为 1 到 64。在这个范围内，Swift `String.prefix(64)` 按字形簇截取是空操作（字形簇数不超过码点数），所以不存在跨平台的切分差异。
  3. 逐个码点做完整小写映射，不考虑上下文（Swift `lowercased()` 的行为；安卓对每个码点单独调用 `String(Character.toChars(cp)).lowercase(Locale.ROOT)`，以避开 Java 对希腊字母词尾 sigma 的上下文规则）。小写结果的每个码点也须满足第 1 步。
  4. 加前缀 `t:`，再做 NFC（Swift `precomposedStringWithCanonicalMapping`，安卓 `java.text.Normalizer.normalize(s, NFC)`）。
  5. 结果的标签部分不超过 128 个 UTF-8 字节。
- 接收方检查：标签部分满足第 1 步的码点条件、是 NFC、不超过 128 字节，且对它再做一遍第 3、4 步结果不变（幂等检查）。码点限定在 Unicode 13.0 的已分配 BMP 字符内，三端的小写与 NFC 数据在这个范围里结果相同（Unicode 的稳定性政策保证已分配字符的规范分解不再改变；S0 用金样本覆盖大小写映射）。
- 本机键与同步键的关系：Swift 端 `Taste.tagKey(r)` 与第 1 到 4 步在 `String` 身份上相等（`tagKey` 没有 NFC，但 Swift 按规范等价判等），所以 `veto` 投影能直接命中 `room.tags` 算出的本机键。
- 金样本覆盖：ASCII、大写、带 `#`、预组合与分解的 `é`、`ΣΑΣ`、`İ`、`ß`、`ǅ`、64 与 65 个码点、BMP 外码点（emoji）、Unicode 13.0 之后才分配的码点、私用区、含空格、含引号与反斜杠、小写后超过 128 字节。期望值由 S0 的 Go 生成器按上述规则算出，Swift 与 Kotlin 都必须一致。

### 6.4 本地操作到寄存器的映射（写死）

每行一个 tick，记作 `h`。「写 X」= 把寄存器 X 设为 `h` + 载荷。前置条件按操作发生时的本机投影（第 6.5 节）判断；不满足就不写任何寄存器。

| 本地操作（现有函数） | 前置条件 | 同步写入 |
|---|---|---|
| `Curation.favoriting(x)` | 键合法 | `f = h+`，`b = h-`；显示原文与键不同，或该条目已有 `n` 时，写 `n = h` + 原文（显示原文不合 `n` 的格式时用键） |
| `Curation.restoringFavorite(x)` | `canRestoreFavorite(x)` 为真（未屏蔽、未收藏）；否则现有函数原样返回，这里也不写 | 同 `favoriting` |
| `Curation.unfavoriting(x)` | 当前是收藏 | `f = h-` |
| `Curation.blocking(x)` | 键合法 | `b = h+`，`f = h-`，`n` 规则同上 |
| `Curation.unblocking(x)` | 当前是屏蔽 | `b = h-` |
| `Curation.importing(names)`（同步开启时） | 见下方「导入」 | 每个入选的名字按 `favoriting` 写入 |
| `Taste.vetoing(k)` | 第 6.6 节的「不想看」总额未满；`k` 在同步域内则走同步，否则只在本机 | 同步域内：`veto.k = h+` |
| `Taste.restoring(k)`、`boosting(k)`、`removing(k)` | 本机该键当前 vetoed，且在同步域内 | `veto.k = h-` |
| `Taste.resettingProfile()`、`erased()`（清除全部偏好） | 至少一个寄存器为 `+` | 对每个寄存器为 `+` 的键写 `veto.k = h-`（共用一个 `h`） |
| 设置页切换 `publicOnly`、`infoAlwaysOn` | 用户主动切换 | `settings.k = h` + `1`/`0` |
| `rejecting`、`following`、`recording`、`settingPaused`、`marking(seen:)` | — | 不写 |

- 成对记账：收藏时一并写屏蔽的 `-`（反之亦然）。它覆盖的情况是：对方有一条本机还没见过、时间更早的屏蔽。只写 `f+` 的话，用户之后取消收藏时，那条旧屏蔽会冒出来。
- 导入（同步开启时，用户裁决「导入排在最前」）：
  1. 固定窗口：按文件顺序去掉不合规名字、按键去重，取前 300 个。窗口只由文件内容决定，与当前收藏状态无关。
  2. 过滤：去掉窗口里此刻已是收藏或屏蔽的名字。
  3. 剩下的从末尾往前逐个 tick，按 `favoriting` 写入，所以文件里排在前面的名字更新。
  4. 执行 `E`。窗口内的名字是此刻最新的收藏，必然全部保留；原有收藏可能被挤掉，确认文案写出数量。
  - 幂等：同一文件第二次导入时窗口相同，窗口里的名字都已是收藏，第 2 步过滤后为空，不产生写入。用户在两次之间删掉的名字会被重新加入，这是预期行为。
  - 同步关闭时保持现有 `Curation.importing` 的语义（原有收藏在前、新名字接在后面），不改。
- 只有用户操作产生寄存器写入。读取失败返回的空值、只读状态、坏文件改名备份、`E` 的裁剪、体积裁剪、`Taste.trimmed` 的裁剪，一律不产生写入。

### 6.5 投影（同步文档 → 本机视图；不写回文档）

- 收藏中：`f` 为 `+`，且 `b` 不为 `+` 或 HLC(`f`) > HLC(`b`)。
- 已屏蔽：`b` 为 `+`，且 `f` 不为 `+` 或 HLC(`b`) ≥ HLC(`f`)。即两边都在时 HLC 大者胜，平局屏蔽胜。
- 顺序：按生效寄存器的 HLC 降序（最新在前，与 `Curation` 的数组语义一致）；HLC 相同时按键的 UTF-8 字节升序。
- 显示名：有 `n` 用它的载荷，否则用键。
- 本机 `Curation` = 收藏投影与屏蔽投影（各不超过 300，由 `E` 保证），交给 `Curation(favorites:blocked:)` 时不会再被裁剪。
- 口味：新增纯函数 `Taste.settingSyncedVeto(_ key: String, _ vetoed: Bool) -> Taste`（S1 实现），只用于投影：
  - `vetoed == true`：已有 belief 只把 `vetoed` 设为 true；没有就新建 `Belief(vetoed: true)`（`at = 0`，各计数为 0）。
  - `vetoed == false`：已有 belief 只把 `vetoed` 设为 false；若此时 `hit`、`miss`、`hits`、`misses` 全为 0，删除该条目。
  - 不改 `at`、`hit`、`miss`、计数，不触发学习事件。对同一文档重复投影，结果不变。
  - 本机用户主动的 `restoring` 保持原有语义（清零落空证据），只是同时写一个 `veto` 寄存器。
- 设置：按载荷写入 `SettingsStore`；文档里没有的键，本机值保持不变。
- 投影在每次合并之后与启动时各重建一次，以修复本机文件与同步状态的偏差。

### 6.6 容量上限与裁剪函数 `E`（写死）

上限从源头对齐本机：

| 类别 | 判定 | 上限 | 保留前 N 个的全序（先比第一个键，相同再比下一个） |
|---|---|---|---|
| 在用收藏 | 第 6.5 节「收藏中」 | 300（`Curation.maxEntries`） | HLC(`f`) 字节降序；房间键字节升序 |
| 在用屏蔽 | 第 6.5 节「已屏蔽」 | 300（`Curation.maxEntries`） | HLC(`b`) 字节降序；房间键字节升序 |
| 房间墓碑 | 条目既不是收藏也不是屏蔽 | 1,000 | 条目内 `f`、`b`、`n` 三个寄存器 HLC 的最大值字节降序；房间键字节升序 |
| 「不想看」在用（同步） | `veto` 载荷 `+` | 450 | HLC 字节降序；口味键字节升序 |
| 「不想看」墓碑 | `veto` 载荷 `-` | 500 | HLC 字节降序；口味键字节升序 |

- 键在各自的映射里唯一，所以每个全序都没有平局。
- `E(D)`：对每个类别按上表排序，删除排名超出上限的整个条目（房间类删整个房间条目，包括它的 `f`、`b`、`n`）。`E` 只删除，从不写入，所以不产生墓碑，也不改动任何保留下来的寄存器。
- `E` 在每次合并之后、每次本地操作之后、保存与推送之前执行。
- 与本机语义的对应：在用收藏、屏蔽超出 300 时删掉最旧的，就是 `Curation`「超出丢最旧的」。并发添加使合并结果超过 300 时，被删的也是排在最后、本机本来就不会显示的那些。用户的明确操作只要还在上限之内，就不会被丢。
- 「不想看」的 500 总额（`Taste.maxBeliefs`）：同步的在用「不想看」不超过 450，本机专用（同步域外）的「不想看」不超过 50，两者合计不超过 500，所以 `Taste.trimmed`（vetoed 强度无穷大）不会裁掉任何一个。同步开启时，`vetoing` 在对应额度已满时拒绝，提示「不想看最多 450 个（另有 50 个本机专用）」。开启同步时本机专用的已超过 50 个，按口味键字节升序保留前 50 个，其余在开启前的说明页列出并取消。另外，S1 把 `Taste.trimmed` 的排序补上平局规则（强度相同按键字节升序），使裁剪结果确定。
- 已知残余：被 `E` 删掉的墓碑或超限项，可能被一台仍持有旧值的离线设备带回来，表现为一个旧收藏、旧屏蔽或旧「不想看」重新出现，用户可以再删一次。

### 6.7 体积（写入前实测，按压缩前计量）

- 上限写死：明文 JSON（第 7.3 节的紧凑写法）不超过 `P = 600,000` 字节，按压缩前计量。
- 每次保存或推送前，先执行 `E`，再编码并实测字节数：
  1. 不超过 `P`：照常。
  2. 超过 `P`：按「最旧墓碑」全序依次删除墓碑，直到不超过 `P` 或墓碑删完。全序为：寄存器 HLC 字节升序；同 HLC 时房间墓碑在前、「不想看」墓碑在后；再按键字节升序。删除墓碑不产生写入。
  3. 墓碑删完仍超过 `P`：
     - 由本地操作引起：拒绝这次操作（文档与本机视图都不变），提示「同步数据已满，请删掉一些收藏、屏蔽或不想看」。
     - 由合并引起：保留合并结果在本机（它满足数量上限），停止推送，设置页提示同样的文案，直到用户删减到上限以内。
- 估算：数量上限下，`n` 限定为 ASCII、标签限定 128 字节且不含需转义的字符，在用部分最大约 400 KB，典型用户约 22 KB（压缩后约 10 KB）。这些数字只作参考，上限以实测为准；S0 用金样本给出一份接近上限的文档与它的实测字节数。
- 接收方：解密、解压后的明文超过 `P` 即非法。

## 7. 合并（确定性函数，三端逐位一致）

### 7.1 规则

`merge(A, B) = E(U(A, B))`，随后按第 6.7 节做体积处理：
- `U`：`schema` 两边都必须是 2；`rooms`、`veto`、`settings` 各自键取并集，同键逐字段取寄存器的字节序较大者，一边缺就取另一边。
- 再执行 `E`。

### 7.2 承诺与证明方式

- 确定性：`merge` 是两份文档的纯函数，三端对同样的输入得到逐字节相同的结果（键序不计）。`U` 交换，`E` 是 `U` 结果的函数，所以 `merge(A, B) = merge(B, A)`；对合法文档 `merge(A, A) = A`。
- 最终一致：所有副本见过同一组操作，且停止新操作后继续互相同步，各副本的文档相同、且不超过任何上限。
- 不承诺：裁剪之后的结合律，以及「被裁掉的条目与合并顺序无关」。第三轮审查给出了反例：同一组输入按不同分组合并，可能留下不同的超限项。
- 证明方式是测试，不是纸面推导（第 18 节 S0、S1、S4）：
  - S0 的 Go 参考实现按固定种子生成 `simulation[]` 用例并物化成脚本（每个副本的操作序列、两两合并的顺序、重复合并），写出每一步之后各副本的期望文档。三端按脚本回放，结果必须与金样本逐项相等。脚本物化之后，三端不依赖各自的随机数生成器。
  - 每端另跑本端的随机模拟：N 个副本（2 到 6）随机增删收藏、屏蔽、「不想看」，含快钟设备与超过各上限的操作量，按随机顺序两两合并、重复合并，最后进入收尾阶段（所有副本依次与同一个「服务端」副本同步，直到连续两轮无变化）。断言：各副本文档相同；每个类别不超过上限；在任何时刻都处于上限之内的操作全部生效。至少 1,000 组，固定种子写进测试，失败时打印种子。

### 7.3 合法性（不满足就整份拒收：不合并、不推送、保留本地，界面提示）

- 解析器：三端都用自带的严格 JSON 解析器（S1、S4 实现；不用 `JSONSerialization` 或 `org.json`，二者分别对重复键沉默或过于宽松）。规则：RFC 8259 严格子集；输入必须是合法 UTF-8，不带 BOM；拒绝重复键（按字节判断）；不允许 `\u` 转义（合法文档的字符串里不需要任何转义）；数字只允许出现在 `schema`；对象嵌套不超过 3 层；明文不超过 `P`。
- 写出：紧凑 JSON（无多余空白），字符串按 UTF-8 原样写出。合法文档的字符串里不含 `"`、`\` 与控制字符，所以写出时不需要转义。键序不限。
- `schema` 必须恰为 2；大于 2 进入只读（见第 3 节），不算非法；其余值非法。
- 形状符合第 6.1 节，键与载荷符合第 6.2、6.3 节，所有 HLC 满足第 5.1 节的静态界限。
- 数量不超过第 6.6 节上限。诚实写入方推送前都执行过 `E`，超限说明对方实现有误，按非法处理。

## 8. 加密封装（写死）

- 载荷 = 1 字节格式标记 + 正文：
  - `0x00`：正文为明文 JSON 原文。
  - `0x01`：正文为明文 JSON 的 raw DEFLATE（RFC 1951，无 zlib 头尾）。
  - 写入方压缩一次；压缩结果比原文短才用 `0x01`，否则用 `0x00`。压缩只是优化，载荷长度因此必然不超过 `P + 1`。
  - 压缩参数：Apple 用 `Compression` 框架的 `COMPRESSION_ZLIB`（即 raw DEFLATE），一次性编码；安卓用 `Deflater(6, true)`，输入一次给完后 `finish()`，不做中途刷新。各端压缩字节不要求相同。
  - 解压规则：流式计数，超过 `P` 立即中止；流必须以末块（BFINAL=1）正常结束；结束后不得有剩余输入（安卓 `Inflater(true)` 在输入末尾补 1 个 0 字节，结束时 `getRemaining()` 必须恰为 1；Apple 流式解码结束时源数据必须恰好用完）；截断按非法处理。
  - 合并、寄存器比较与文档相等都在解压后的 JSON 上进行，与压缩字节无关。
- 信封 = ASCII `e1.` + base64url(nonce) + `.` + base64url(ciphertext ‖ tag)。
  - nonce：12 字节，每次封装由系统 CSPRNG 新生成；随机源报错即中止。
  - tag：16 字节。
  - AAD = ASCII `vela-sync/e1|` + blobID（64 个小写 hex）+ `|` + 该信封将要存放的版本号（第 4.2 节十进制）。
- Apple：`AES.GCM.seal(payload, using: SymmetricKey(data: encKey), nonce: AES.GCM.Nonce(data: nonce), authenticating: aad)`，取 `.ciphertext` 与 `.tag` 拼接；不用 `.combined`（它含 nonce）。解封用 `AES.GCM.SealedBox(nonce:ciphertext:tag:)`。
- 安卓：`Cipher.getInstance("AES/GCM/NoPadding")`，`GCMParameterSpec(128, nonce)`，`updateAAD(aad)`；`doFinal` 输出本来就是 ciphertext ‖ tag。
- 网络重试（同一 base 的同一请求）原样重发同一个信封；凡是重新合并（如 409 之后），一律重新封装并换新 nonce。
- nonce 碰撞概率约为 q²/2^97（q 为同一 `encKey` 下的累计加密次数，含失败重试），三台设备十年约 6e-18，可以忽略。不得改成计数器 nonce，因为多台设备共用 `encKey`。
- 尺寸写死（由载荷上限精确推出，不依赖压缩率）：ciphertext ‖ tag 不超过 600,017 字节，base64url 不超过 800,023 个字符，信封不超过 800,043 字节，取上限 **800,100 字节**；请求体上限 **802,048 字节**。

## 9. 写入认证（写死）

- 每次写操作都用 `signSeed` 签名（RFC 8032 纯 Ed25519，无预哈希、无上下文）。签名 64 字节，传输时用 base64url（86 个字符）；公钥用 base64url（43 个字符）。
- 被签消息 = 以下 6 行 ASCII，用 `0x0A` 连接，末尾不加换行：
  1. `vela-sync/v2/` + op，op ∈ `put` | `delete`
  2. blobID
  3. epoch（服务端纪元，32 个小写 hex，取自本周期最近一次响应）
  4. base（请求所基于的当前版本，十进制；创建时为 `0`）
  5. next = base + 1（十进制；base 最大为 2^53−2）
  6. put 时为小写 hex(SHA-256(信封的 ASCII 字节))；delete 时为单个 `-`
- 服务端用该行登记的 `pub` 验签。创建（base = 0）时请求体带 `pub`，服务端用它验签并登记。之后 `pub` 不再改变。
- 防重放：
  - 同一空间内：版本只增不减，同一签名只在版本恰为 base 时有效，成功一次后再次提交得到 409。
  - 删除之后：服务端保留该 blobID 的删除墓碑，任何写请求（包括重放的旧首写、旧 PUT、旧 delete）一律 410，空间不可重建（第 10.2 节）。所以同一 blobID 的版本号永远不会从 0 重新开始，同一 `(blobID, next)` 至多被接受一次。
  - 跨恢复：恢复备份后运维必须轮换 epoch（第 10.4 节），恢复前签过的请求带旧 epoch，一律 403。
- 抢注：只有在创建请求途中能看到并拦截请求的一方（Cloudflare、服务端本身）才可能抢先用自己的公钥创建。客户端每次 GET 后核对返回的 `pub` 等于本机派生的 `pub`（或用第 4.1 节的核对消息），不一致即报「同步空间被占用」，不写入。这是在途方的可用性攻击，接受为残余风险。
- 签名只证明「持码者写的」，挡不住服务端删除、隐瞒或回滚数据。这些由第 11.4 节的停写规则与各设备本地数据兜底。

## 10. 服务端

### 10.1 接口

所有响应都是 `Content-Type: application/json`、`Cache-Control: no-store`，JSON 响应都带 `epoch` 与 `now`（毫秒）。

| 请求 | 成功 | 失败 |
|---|---|---|
| `GET /v2/blob/{id}` | `200 {"ver":n,"pub":"…","data":"<信封>","epoch":"…","now":…}` | `404 {"epoch":…,"now":…}` 从未存在；`410 {"deletedAt":毫秒,"epoch":…,"now":…}` 已删除 |
| `PUT /v2/blob/{id}`，体 `{"base":n,"data":"…","sig":"…","pub":"…"}`（`pub` 仅 `base=0` 时必带，其余时候不得带） | `200 {"ver":n+1,"epoch":…,"now":…}` | `409 {"ver":当前,"pub":…,"data":当前,"epoch":…,"now":…}`；`403` 验签失败（含 epoch 不符）；`404` 行不存在且 base≠0；`410` 已删除；`413`；`429`；`507` 配额已满 |
| `POST /v2/blob/{id}/delete`，体 `{"base":n,"sig":"…"}` | `200 {"epoch":…,"now":…}`，行转为删除墓碑 | `409`（附当前）；`403`；`404`；`410` 已删除 |

- `id` 必须匹配 `^[0-9a-f]{64}$`，否则 400。`base` 为 0 到 2^53−2 的整数，越界 400。信封须匹配 `^e1\.[A-Za-z0-9_-]{16}\.[A-Za-z0-9_-]{22,}$` 且不超过 800,100 字节。
- 版本放在请求体，不用 `If-Match` 头，避免中间代理改写条件头。
- 没有列表、枚举、搜索接口。未知路径一律 404。

### 10.2 存储与原子性

- SQLite（WAL，`synchronous=FULL`，`busy_timeout` 5 秒）：
  - `blobs(id TEXT PRIMARY KEY CHECK(length(id)=64), ver INTEGER NOT NULL, pub BLOB NOT NULL CHECK(length(pub)=32), data TEXT NOT NULL, size INTEGER NOT NULL, created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL)`；
  - `deleted(id TEXT PRIMARY KEY CHECK(length(id)=64), deleted_at INTEGER NOT NULL, last_epoch TEXT NOT NULL, last_ver INTEGER NOT NULL)`：删除墓碑，永久保留，不可复用；
  - `creations(ts INTEGER NOT NULL, ip_bucket TEXT NOT NULL)`：创建计数（第 10.3 节），按 `ts` 建索引，只保留最近 2 天；
  - `meta(key TEXT PRIMARY KEY, value TEXT NOT NULL)`：存 `epoch`（数据库初始化时由 `secrets.token_hex(16)` 生成）。
- 每个写请求在一个 `BEGIN IMMEDIATE` 事务里完成，顺序固定：
  1. 查 `deleted`：命中即回滚并返回 410（在验签之前，所以重放的旧首写无法生效）。
  2. 读行、验签、版本检查。
  3. 配额与创建频率检查（第 10.3 节，同一事务内用 `SELECT count(*), total(size) FROM blobs` 与 `creations` 计数）。
  4. 写入：`UPDATE … WHERE id=? AND ver=?`，影响行数必须为 1，否则回滚并返回 409（附同一事务里读到的已提交数据）；创建用 `INSERT`，主键冲突时回滚并返回 409 与当前行，创建成功同时插入一行 `creations`。
  5. COMMIT。
- 已存在的行收到 `base=0` 返回 409；不存在且不在 `deleted` 的行收到 `base≠0` 返回 404，不创建。
- 删除：同一事务内验签、版本检查，然后 `DELETE FROM blobs` 并 `INSERT INTO deleted`（记录删除时刻、当时的 epoch 与最后版本）。空间数与字节配额立即释放；`deleted` 行每行约 100 字节，增长速度受创建频率限制（每天至多 50 个），不计入配额。

### 10.3 来源、限流与配额

- 进程只监听 `127.0.0.1`，cloudflared 在同机转发；主机上没有其他通向该端口的转发（部署验收要核查）。
- 只信任 `CF-Connecting-IP`：缺失、重复或不是合法 IPv4/IPv6 时返回 400；忽略 `X-Forwarded-For` 等其他头。IP 桶：IPv4 按单个地址，IPv6 按 /64。
- 短周期频率（内存中，滑动 60 秒窗口；超出返回 429 与 `Retry-After` 秒数）：
  - 每个 IP 桶：所有请求每分钟 120 次；验签失败每分钟 5 次。
  - 每个空间：成功写入每分钟 30 次。验签失败不计入该空间的额度。
  - 全局：写入每分钟 600 次。
  - 内存状态按 LRU 最多 10,000 个桶。被淘汰的桶从零开始计数，最坏结果只是该桶在一分钟内多获得一次额度。
- 创建频率（在 SQLite 的 `creations` 表里计数，进程重启与 LRU 淘汰都不会清零）：
  - 每个 IP 桶：过去 3,600 秒（滑动窗口）内不超过 3 次；当前 UTC 自然日内不超过 10 次。
  - 全局：当前 UTC 自然日内不超过 50 次。
  - 超出返回 429，`Retry-After` 为窗口剩余秒数。`creations` 只保留最近 2 天，每次创建时顺带删除过期行。
- 配额（按空间计量，更新同样受约束，检查与写入在同一事务内）：
  - 单个空间：信封不超过 800,100 字节，每次 PUT 都检查。
  - 全局空间数：达到 5,000 时拒绝创建（507）。
  - 全局总字节（`total(size)`，即所有信封字节之和）：创建前若总量已达 214,748,364 字节（256 MiB 的 80%）则拒绝创建；更新后若总量超过 268,435,456 字节（256 MiB）则拒绝该更新（507）。留出的 20% 是已有空间增长的余量。
  - 数据库文件、WAL 与可选备份的实际占用约为信封总字节的 2 到 3 倍，部署时按 1 GB 磁盘预算核查。
- 残余风险：匿名者在频率限制内持续创建空间，最终可以占满全局配额，使新用户无法创建。对策是运维告警（总量达到 70% 时由 healthcheck 报出），由运维人工处置；不做闲置空间自动清理，因为那会删掉真实用户的数据。
- HTTP 资源：头部总长不超过 8 KiB；写请求必须带 `Content-Length`（缺失返回 411），不接受 `Transfer-Encoding`（返回 400）；先检查长度，超过 802,048 字节直接 413、不读体；从连接建立到读完请求体的总时限 10 秒（整体截止时间，不是每次读取的超时）；并发连接上限 32。

### 10.4 日志、缓存与可选冷备份

- 改写访问日志：只记时间、方法、路由模板（`/v2/blob/:id`）、id 前 8 位、状态码、体积档位、IP 前缀（IPv4 /24，IPv6 /48）。不记请求头、请求体、签名、公钥、完整 id。journald 保留 14 天。
- Cloudflare：该主机名设置缓存规则「绕过缓存」，不开日志推送。Cloudflare 边缘本身看得到完整路径与请求体，我们控制不了，威胁模型按它可见处理。
- 冷备份是可选项，只用于服务器重建：每日用 `sqlite3.Connection.backup()` 生成一致性快照，文件权限 0600，目录仅 root 可读，保留不超过 7 天。
- 本协议不定义「恢复后继续用原空间」的语义。恢复快照后运维必须立即用新随机值替换 `meta.epoch`（RUNBOOK 写成恢复的第一步，S5 演练）。客户端发现 epoch 改变，或版本低于已见水位，就停写并提示关闭再重开（第 11.4 节）。快照之后才删除的空间会随恢复回到 `blobs` 表，但所有已加入设备都会因 epoch 改变而停写，旧签名也因 epoch 不符而无效。

### 10.5 实现约束

- Python 3 标准库（`http.server.ThreadingHTTPServer`、`sqlite3`、`hashlib`、`hmac`、`json`、`secrets`）加 Ubuntu 系统包 `python3-cryptography`（apt 安装，不用 pip）。验签：`Ed25519PublicKey.from_public_bytes(pub).verify(sig, msg)`，捕获 `InvalidSignature` 返回 403。
- systemd：`NoNewPrivileges`、`ProtectSystem=strict`、`ReadWritePaths` 只到数据目录、`MemoryMax=128M`、专用用户。

## 11. 客户端同步流程

### 11.1 本地同步状态（同步开启期间的唯一事实来源）

- 文件 `sync-state.json`（与 `feed-curation.json` 同目录）字段：
  - `phase`（第 12.1 节）、`origin`、`blobID`、`epoch`；
  - 文档；HLC `(l, c)`；`maxSentL`；
  - `gen`（本地操作计数）、`pushedGen`；
  - 水位 `lastSeenVer`、`lastSeenHash`（最近一次已验证信封的 SHA-256）；
  - 待确认请求 `inflight`：`base`、`next`、信封哈希、`sentGen`，没有在途请求时为空；
  - 加入计划 `joinPlan`（第 12.4 节）；
  - 迁移标记；`oversize` 标记（第 6.7 节第 3 步的合并情形）；最近成功与失败信息。
- 该文件排除出备份（Apple 设 `isExcludedFromBackup`，安卓写进备份排除规则）。
- 读写沿用 `PreferenceQuarantine` 口径：读失败就把坏文件改名备份，同步进入「暂停：同步状态损坏」，不推送，提示关闭再重开（或在钥匙串里的 `K` 仍可用时，提供「用同一同步码重新加入」）。改名也失败时只读，同样暂停。空读永不解释为「用户删光了」。
- 写顺序：用户操作 → 内存中文档写入寄存器、执行 `E` 与体积检查、`gen` 加一 → 同步写 `sync-state.json`（原子替换，主线程外的串行队列，完成后才确认操作）→ 由投影派生 `Curation` 与 `Taste` 的变化，按现有方式（`DeferredSaver`）保存。`sync-state.json` 写失败时，本次操作在内存中仍生效，界面提示「保存失败」，下次操作时重试；这次操作不会被当作已同步。
- 启动时若同步开启：先读同步状态，再用投影覆盖本机收藏与「不想看」，修复两份文件的偏差。

### 11.2 协调器（每个空间一个，串行）

一次同步周期：
1. GET。
2. 校验 epoch 与水位（第 11.4 节），核对 `pub`，解密（AAD 用响应里的 `ver`），校验文档。通过后，`epoch` 写入（首次）或核对，`lastSeenVer`、`lastSeenHash` 推进为该响应的值，立即落盘。不管这一周期之后是否推送，水位都在这里推进。
3. 若 `inflight` 非空：`ver == inflight.next` 且信封哈希等于 `inflight` 的哈希时，确认推送成功，`pushedGen = max(pushedGen, inflight.sentGen)`；其他情况不确认（重新合并推送是安全的）。然后清空 `inflight` 并落盘。
4. `L = merge(L当前, R)`，并做体积处理。合并的是此刻内存里的当前状态，而不是发起请求时的快照，所以请求期间新增的改动不会丢。随后推进 HLC，保存状态，有变化时更新投影。
5. `L` 与 `R` 相等且 `gen == pushedGen` 时结束（不做无意义的 PUT）。`oversize` 为真时也结束（不推送）。
6. 否则执行第 5.2 节的发送前检查，以 `next = ver + 1` 封装并签名。先把 `inflight`（base、next、哈希、`sentGen = gen`）与新的 `maxSentL` 落盘，再 PUT `base = ver`。
7. 200：`lastSeenVer = next`，`lastSeenHash` = 本次信封哈希，`pushedGen = max(pushedGen, sentGen)`，清空 `inflight`，落盘。请求期间产生的新操作让 `gen > pushedGen`，留到下一周期。
8. 409：响应体当作新的 GET 结果，回到第 2 步。一个周期最多重试 3 次，超过就退避，`gen > pushedGen` 保留。
9. 超时或连接中断：保留 `inflight`，下一周期第 3 步处理。
- 关闭、清除、加入开始时，协调器取消在途请求，并递增内部令牌；令牌不符的迟到响应一律丢弃，不写状态。

### 11.3 触发时机（无轮询、无常驻连接）

- 启动、回到前台：一个周期。
- 本地操作：去抖 5 秒后一个周期；同一设备两次 PUT 间隔至少 10 秒。
- 打开收藏面板、口味面板、同步设置页：距上次成功 GET 超过 60 秒才发一个周期。
- 进后台或退出：`gen > pushedGen` 时尽力推一次（iOS 用 `beginBackgroundTask`，macOS 在退出流程里最多等 3 秒），不保证完成；未完成的下次启动会补推。
- 设置页「立即同步」。
- 失败退避：30 秒起翻倍，最长 1 小时；429 按 `Retry-After`。退避期内的触发直接跳过。

### 11.4 错误分类（失败可见、不打扰）

| 情况 | 处理 |
|---|---|
| 断网、超时、5xx、非 JSON 或截断的响应（如中间页的 HTML） | 暂时故障：退避后重试，不停用、不弹窗 |
| 429 | 按 `Retry-After` |
| 507 | 「服务器空间已满」：停止推送，退避 1 小时后再试 |
| 403 | 「云端拒绝了这台设备的写入」：停止自动写，保留一切，提示关闭再重开 |
| 410 | 停止同步，保留本地数据与同步状态，提示：「这个同步空间已于 <本地日期> 被清除。请关闭同步后重新开启（会生成新的同步码），或输入新的同步码。本机数据都还在。」 |
| 404，且本机 `lastSeenVer > 0` 或 `inflight` 非空 | 「云端同步空间不见了」：停止同步，保留本地，提示关闭再重开；不自动创建。只有 `lastSeenVer == 0` 且 `inflight` 为空（从未创建成功、也没有结果未知的创建）时，404 才走创建 |
| epoch 与已记录的不同 | 「云端已重置」：停写，保留本地，提示关闭再重开 |
| 回滚：`ver < lastSeenVer`，或 `ver == lastSeenVer` 但信封哈希不同 | 同上：停写，不合并，提示关闭再重开 |
| 413、本机体积超限 | 「同步数据已满」（第 6.7 节），停止推送 |
| 未知信封前缀、schema 更大 | 只读，提示更新 App |
| 文档非法（第 7.3 节） | 不合并、不推送，提示，保留现场 |
| AEAD 解封失败 | 下次触发重试一次；连续两次（不同周期）失败才暂停，保留 `K`、本地数据与 `gen` |
| `pub` 与本机派生不一致 | 「同步空间被占用」：停止写入，提示关闭再重开 |
| 本机时间与服务端相差超过 1 小时 | 暂停写入，提示校准时间 |

- 设置页显示：上次成功同步时间、是否有待同步的改动、最近一次失败的类别。除加入确认、上表中提示「关闭再重开」的几类、410、「空间被占用」以外不弹窗。
- 「关闭再重开」是唯一的恢复路径。它不丢数据：投影落盘屏障（第 12.2 节）先把本机数据写稳，然后本地数据作为新空间的首份上传。

## 12. 开启、加入、关闭、清除、泄露处置

### 12.1 持久化步骤与启动检查

- 钥匙串（或 Keystore）里是一个条目，内容为 `{K, dev, blobID}` 的 JSON，一次写入，原子生效。同步状态里有 `phase` ∈ `creating` | `joining` | `active` | `disabling` | `clearing`。
- 启动时按下表处理组合状态，不得把「缺一项」一律当成「未开启」：

| 同步状态 | 钥匙串条目 | 处理 |
|---|---|---|
| 无 | 无 | 未开启 |
| 无 | 有 | 「同步状态丢失」：提供「用同一同步码重新加入」（第 12.4 节，需确认）或「关闭」（删条目） |
| `creating` | 无 | 创建未完成：删除状态，未开启 |
| `creating` | 有，blobID 一致 | 从创建第 5 步继续 |
| `joining` | 无 | 加入未完成：删除状态，未开启，提示重新粘贴 |
| `joining` | 有，blobID 一致 | 按第 12.4 节「恢复」继续 |
| `active` | 无 | 「同步密钥丢失，请重新输入同步码」 |
| `active` | 有，blobID 一致 | 正常 |
| `disabling` | 任意 | 先执行投影落盘屏障，再继续关闭流程 |
| `clearing` | 有 | 先执行投影落盘屏障，再继续清除流程 |
| `clearing` | 无 | 先执行投影落盘屏障，再继续关闭流程的剩余步骤 |
| 任意 | 有，blobID 不一致 | 停止同步，提示关闭再重开；不自动选择其中一个 |

- 钥匙串暂时不可用（首次解锁前、Keystore 暂时性错误）时不做任何判断，本次跳过同步。

### 12.2 投影落盘屏障（关闭、清除、加入、切换空间之前必须执行）

问题：同步开启时，本机 `Curation` 与 `Taste` 文件是延迟保存的投影（`DeferredSaver` 默认延迟 2 秒，`flush()` 不报告成败）。若先删掉同步状态再崩溃，最近的操作只存在于已删掉的同步状态里。

屏障步骤：
1. 取消 `curationSaver` 与 `tasteSaver` 中尚未写出的值（下一步会写出更新的值）。
2. 从同步状态的文档重新计算投影，得到 `Curation` 与 `Taste`（第 6.5 节）。
3. 直接调用 `CurationStore.save(_:)` 与 `TasteStore.save(_:)`，两者都返回 `true` 才算通过（这两个函数已经返回 `Bool`，并在只读状态下返回 `false`）。设置在投影时已同步写入 `UserDefaults`，这里调用一次 `synchronize()` 作为提示即可。
4. 任一返回 `false`：中止当前流程，同步状态与钥匙串都不动，提示「本机保存失败，未做任何更改」。
5. 通过后才能修改 `phase`、钥匙串或云端。

中断恢复：屏障写的是普通本机文件，可以重复执行。各流程都把「删除同步状态」放在最后一步，所以启动时只要看到 `disabling` 或 `clearing`，同步状态就还在，先重跑屏障再继续（第 12.1 节表格）。

### 12.3 创建（「在这台设备上开启同步」）

1. 前置：启动时保留的收藏与口味读取结果必须是「正常读取」或「文件不存在」（第 14.1 节），否则拒绝开启并说明原因。
2. 说明页：将上传哪些数据、同步码等于全部权限、丢码不可恢复、不合规名字与超额本机专用「不想看」的处理（第 14.1 节）。用户同意。
3. 生成 `K` 与设备号，派生 blobID、`pub`。写同步状态 `phase = creating`（含 blobID、origin，不含 `K`），再写钥匙串条目。
4. 迁移盖章（第 14.1 节，全部盖章），执行 `E` 与体积检查，写同步状态 `phase = active`。
5. 同步周期：GET 404（且满足第 11.4 节的创建条件）后创建（base=0 带 `pub`）。GET 返回 200：先核对 `pub`，再按普通周期合并。GET 返回 410：停止，提示「生成的空间标识已被使用，请重试」，删除状态与钥匙串条目后从第 3 步重来（概率可忽略，只为完整）。
6. 显示同步码与短指纹，要求用户保存；提供复制（敏感标记）。

### 12.4 加入（「我已有同步码」；用户裁决：合并，两边都保留）

1. 前置同创建第 1 步。若本机已在另一个空间，先执行本机关闭（第 12.5 节，含屏障）。
2. 粘贴，按第 4.3 节严格解析；失败即报无效。
3. 写同步状态 `phase = joining`（含 blobID、origin，不含 `K`）。`K` 只在内存里。
4. GET：
   - 404：提示「这个同步码没有对应的已有空间」，提供「仍用此码创建」（写钥匙串条目、`phase` 改为 `creating`，转入创建第 4 步）或取消。安卓处于「只能加入」级别时不提供创建。
   - 410：提示「这个同步码对应的空间已被清除」，删除状态，不加入。
   - 200：核对 `pub`、epoch，解密并校验；任一失败按第 11.4 节报错，删除状态，不保存 `K`。
5. 计算合并预览：按第 6 步的规则在内存中试算 `merge(本机盖章结果, R)` 并做体积处理，得到计数：
   - N = 将上传的本机收藏数，M = 将上传的本机屏蔽数，V = 将上传的本机「不想看」数；
   - X、Y = 合并后因超过 300 不再保留的收藏、屏蔽数；
   - Z = 本机收藏在云端已屏蔽、将按屏蔽处理的数量。
   确认页显示：「将上传本机 N 个收藏、M 个屏蔽到 <主机名>」，X、Y、Z、V 不为零时各加一行，并显示短指纹与「持有这个同步码的人能看到并修改这些数据」。
6. 用户确认后：写钥匙串条目，再把 `joinPlan` 落盘到同步状态（`origin`、`blobID`、`epoch`、预览时的 `ver` 与信封哈希、计数 N、M、V、X、Y、Z），然后盖章并合并：
   - 本机收藏 x：远端 x 已是屏蔽 → 不盖章（屏蔽优先，与平局规则一致）；远端 x 已是收藏 → 不盖章（保留远端的顺序与时间）；其余情况（远端没有 x、或是墓碑）→ 盖 `f+`，本机的收藏因此保留。
   - 本机屏蔽 x：远端 x 已是屏蔽 → 不盖章；其余 → 盖 `b+`（屏蔽优先）。
   - 本机「不想看」k（同步域内）：远端为 `+` → 不盖章；其余 → 盖 `+`。
   - 本机显式设置：远端没有该键才盖章；远端有值就以远端为准（一个设置无法两边都保留）。
   - 盖章顺序与第 14.1 节相同，然后 `merge(本机盖章结果, R)`，写同步状态（`phase = active`，清空 `joinPlan`），立即推送。
7. 恢复（启动时 `joining` 且钥匙串有条目）：`joinPlan` 存在说明用户已确认。重新 GET 并重算第 5 步的计数：
   - 远端 `ver` 与信封哈希都等于 `joinPlan` 记录的值：计数必然相同，直接执行第 6 步的盖章与合并。
   - 远端已变化，但新计数与 `joinPlan` 的计数完全相同：直接继续。
   - 计数有任何不同：重新展示确认页，用户再次确认后用新计数覆盖 `joinPlan` 再继续；取消则执行本机关闭。
   - `joinPlan` 不存在（确认前崩溃）：删除钥匙串条目与状态，提示重新粘贴。按第 6 步的顺序，确认前不会写钥匙串，所以这一情况只会在确认与写 `joinPlan` 之间崩溃时出现。

### 12.5 多台设备同时首次开启

- 同一个码同时加入（双方都 GET 到 404 再创建）：服务端主键冲突，一方 409，用响应合并后重试，结果是两边的并集。
- 两台设备各点了「创建」，得到两把 `K`：两边永不相遇。引导页明确区分「创建」和「加入」，并提示「其他设备已开启过就选加入」。补救办法：在其中一台选「加入」另一台的码（加入第 1 步会先关闭本机原空间），再在原空间上执行清除（可选）。

### 12.6 本机关闭、清除云端

- 本机关闭：投影落盘屏障 → 写 `phase = disabling` → 删除钥匙串条目 → 删除同步状态。本地收藏与口味保留，其他设备不受影响。这一步撤销不了这台设备曾拿到的码。
- 清除云端：二次确认，文案「将删除云端数据，所有设备停止同步；各设备本地数据保留」。投影落盘屏障 → 写 `phase = clearing` → 签名 delete（base = `lastSeenVer`；409 就用响应里的版本重试；响应丢失时重试，得到 410 或 404 都视为已完成）→ 执行本机关闭的剩余步骤（写 `disabling` 之后的部分）。其他设备之后遇到 410，停止同步并按第 11.4 节提示。
- 清除全部偏好（现有 `clearAllPreferences`）在同步开启时会写 `veto` 的 `-`。文案改为「将清除本机的学习与观看记录，并在所有同步设备上取消『不想看』；收藏与屏蔽保留」。

### 12.7 同步码泄露或设备丢失（用户手动处置，不做自动换码）

1. 在一台可信设备上「清除云端」（第 12.6 节）。旧空间转为删除墓碑，持旧码者再也读不到它，也无法以同一 blobID 重建。
2. 在这台设备上重新「开启同步」：生成新 `K`、新空间，本机数据作为首份上传（第 12.3 节）。
3. 其他每台可信设备：遇到 410 后关闭，再用新码「加入」（合并，两边都保留）。
- 限制写进文案：丢失或泄露期间对方已读到的数据无法收回；丢失的设备本地已有的数据也无法收回。
- 安卓处于「只能加入」级别（第 18 节 S0）时，第 2 步须在 Apple 设备上完成。

## 13. 密钥存储

- Apple：通用密码项，service `com.vela.sync`（不用 `com.vela.stage`，因为 `LegacyLoginCleanup` 会清理那个 service 下的条目），account `space`，值为第 12.1 节的 JSON。`kSecAttrAccessible = kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`，`kSecAttrSynchronizable = false`（显式），不设共享访问组。macOS 用 `kSecUseDataProtectionKeychain = true`。缺少钥匙串授权导致失败（`errSecMissingEntitlement`）的构建视为不支持同步，不退化成明文文件。
- 安卓：`AndroidKeyStore` 里的 AES-256-GCM 包裹密钥（别名 `vela_sync_wrap`），`setUserAuthenticationRequired(false)`，每次包裹用 Cipher 生成的随机 IV。包裹后的条目存进专用 SharedPreferences 文件 `vela_sync`（单个键，一次 `commit()` 写入）。该文件与 `sync-state.json` 都写进 `dataExtractionRules` 与 `fullBackupContent` 的排除项。
- 读取结果分三类，处理不同：
  - 不存在：按第 12.1 节表格判断。
  - 暂时不可用（`errSecInteractionNotAllowed`；Keystore 暂时性错误）：本次跳过同步，稍后再试。
  - 永久失效（Keystore 密钥丢失、`KeyPermanentlyInvalidatedException`、解包失败）：提示「同步密钥丢失，请重新输入同步码」。
- 任何失败都不得自动生成新 `K`。恢复只靠用户保存的同步码。

## 14. 迁移与升级

### 14.1 开启或加入时给已有本地数据盖章（每次开启只做一次，迁移标记存在同步状态里）

- 需要新增的读取接口（现有 API 不提供，列入 S1、S2 的文件范围）：
  - `CurationStore` 与 `TasteStore` 增加 `lastLoadOutcome`（`loaded` | `missing` | `quarantined` | `readOnly`），记录启动时那次读取的结果并一直保留，不因之后再读到「文件不存在」而被覆盖；
  - `SettingsStore` 增加 `hasExplicitValue(forKey:)`（内部为 `defaults.object(forKey:) != nil`）。
- 前置：两个 store 的 `lastLoadOutcome` 都是 `loaded` 或 `missing`，才允许开启或加入。
- 数据源与处理：
  - `Curation` 的收藏与屏蔽数组。键不合规的旧名字不进同步；开启前的说明页列出数量：「N 个格式不合规的旧名字不会同步，将从收藏中移除」。现有入口都会校验用户名，这类名字预计为零。
  - `Taste` 中 `vetoed == true` 的键：`g:` 键与同步域内的 `t:` 键进同步（同步在用上限 450，超出按口味键字节升序保留前 450 个，其余在说明页列出并取消）；同步域外的留在本机（上限 50，规则见第 6.6 节）。
  - `hasExplicitValue` 为真的 `publicOnly`、`infoAlwaysOn`。未设置过的缺省值不盖章，免得用缺省值覆盖其他设备的明确选择。
- 盖章顺序：收藏数组从末尾往前逐个 tick，使原数组第一个（最新）得到最大 HLC，投影顺序与原来一致；屏蔽同理；`veto` 按键的 UTF-8 字节升序；设置按键名升序。迁移只写对应的 `+` 寄存器（以及需要时的 `n`），不写成对的 `-`。
- 创建方全部盖章；加入方按第 12.4 节第 6 步的规则。
- 幂等：迁移标记防止同一次开启重复盖章；导入收藏的幂等见第 6.4 节。

### 14.2 升级与降级

- schema 升级：新版本写出更大的 `schema`，旧客户端进入只读并提示更新；文档在内存中用强类型结构即可（没有未知字段需要保留）。新版本在写出更大的 `schema` 之前，应在界面提示「升级后，尚未更新的设备会暂停同步」。
- 封装版本升级：新客户端能读 `e1` 与新版本，在确认全部设备支持之前继续写 `e1`。
- 派生代升级（`vela3`）：用户关闭再以新码重开。
- 降级（用户装回旧版本）：旧版本遇到更新的 schema 或封装就只读，不覆盖。

## 15. 威胁模型

| 参与方 | 能看到 | 能做 | 不能做 | 对策与残余 |
|---|---|---|---|---|
| Cloudflare 边缘（TLS 在此终结） | 完整路径（含 blobID）、请求头与体（密文、签名、公钥）、IP、时间、体积 | 丢弃、延迟、回送旧响应；在创建请求途中抢先注册 | 解密；伪造或篡改写入；重放已删除空间的旧请求；把旧密文贴上新版本号 | 签名（第 9 节）、删除墓碑（第 10.2 节）、AAD 绑版本（第 8 节）、水位与 epoch 停写（第 11.4 节）；抢注与拒绝服务是残余，可被察觉 |
| 服务端或其运维、被入侵的服务器 | 同上，加上数据库与备份 | 删除、隐瞒、回滚、对不同设备给出不同版本、不轮换 epoch 就恢复备份 | 解密；伪造写入 | 同上；客户端发现回滚即停写，数据以各设备本地为准 |
| 被动网络观察者 | TLS 元数据、访问时间、体积 | 无 | 内容 | TLS |
| 持有同步码者 | 全部同步数据 | 读、改、删空间 | 读本机未同步的口味学习数据；空间删除后重建 | 等同于「把手机交给别人」；处置见第 12.7 节 |
| 诱导粘贴恶意同步码（攻击者控制的主机与 `K`） | 用户确认上传后的数据 | 解密该用户上传的数据 | 用户不确认就拿不到 | 确认页显示主机名与上传数量（第 12.4 节） |
| 丢失或被盗的设备 | 本机数据与 `K` | 以持码者身份读写 | 用户清除云端并重开之后，读写新空间 | 第 12.7 节 |
| 备份泄露（iCloud、安卓备份、服务端快照） | 服务端快照：密文与元数据 | 无 | 解密（`K` 不进任何备份） | 钥匙串与 Keystore 属性、备份排除规则 |
| 滥用存储的匿名者 | 无 | 创建大量空间、灌请求 | 突破单空间与全局配额、绕过创建频率 | 第 10.3 节；占满全局配额是残余，靠运维告警 |

- 元数据泄露：密文体积大致反映收藏与屏蔽的数量，访问时间反映使用时段。接受。
- 前 8 位 id 是可关联标识，不是匿名化；只用于排错，保留 14 天。

## 16. 隐私说明文案要点（开启与加入时展示，设置页可再看）

- 同步的内容：收藏、屏蔽、「不想看」的标签与性别、两个显示设置；不同步观看记录与学习数据。
- 内容在本机加密后才上传；服务器与网络运营方（Cloudflare）看不到内容，但能看到访问时间、大致数据量，并且有能力删除数据或让同步暂时失败。
- 同步码就是钥匙：谁拿到谁就能看到和修改全部同步数据。不要截图分享，不要发给别人。
- 丢了同步码、又没有任何一台已加入的设备，数据无法找回。
- 怀疑同步码泄露或设备丢失：清除云端，重新开启，再在每台设备上输入新码。
- 「清除云端数据」会让所有设备停止同步，各设备本地数据保留；若服务器开启了冷备份，备份中的密文最多再保留 7 天。
- 远端改动在下次打开 App、回到前台、打开收藏或口味面板，或点「立即同步」时出现。
- 收藏与屏蔽各最多保留 300 个，同步的「不想看」最多 450 个，超出时丢掉最旧的。

## 17. 金样本 `Tests/Fixtures/sync/vectors.json`

由独立实现生成：S0 用 Go 标准库（`crypto/hkdf`、`crypto/aes`、`crypto/cipher`、`crypto/ed25519`、`crypto/sha256`、`compress/flate`）写生成器 `scripts/sync/vectors/`，含严格 JSON、HLC、`U`、`E`、体积处理、投影、操作映射、标签规范化（Unicode 13.0 年龄表与大小写、NFC 数据以生成器内嵌的数据文件提供）的参考实现，不依赖三端任何代码。Go 的 Ed25519 签名是确定性的；CryptoKit 的签名带随机性，所以签名一律只做「验证对方的签名」与「自己签的能被验证」，不比字节。

各段字段：
- `kdf[]`：`K_hex`、`salt_hex`、`info`（三条）、`blobID`、`encKey_hex`、`signSeed_hex`、`pub_b64url`、`fingerprint`、`pubcheck_message_hex`。
- `base64url[]` 与 `base64urlInvalid[]`；`decimal[]` 与 `decimalInvalid[]`。
- `code[]` 与 `codeInvalid[]`（第 4.3 节各条）。
- `json[]`：`text`、`valid`、`reason`；覆盖重复键、BOM、`\u` 转义、非法 UTF-8、未知键、缺顶层键、数字出现在 `schema` 之外、`schema` 为 1 或 3、嵌套过深、超过 `P`。
- `tagKey[]`：`raw`、`key`（或 `local_only: true`），覆盖第 6.3 节列出的情形。
- `payload[]`：`json_utf8`、`flag`、`body_b64url`；`payloadInvalid[]`：超过 `P` 的解压炸弹、截断流、末块之后有尾随数据、未知标记字节。
- `envelope[]`：`encKey_hex`、`blobID`、`ver`、`nonce_hex`、`payload_hex`、`aad_hex`、`envelope`（三端必须逐字节相同）；`envelopeInvalid[]`：改 tag、改 AAD 中的版本、截断、错误前缀、填充的 base64、nonce 长度不对。
- `sign[]`：`signSeed_hex`、`pub_b64url`、`op`、`blobID`、`epoch`、`base`、`next`、`envelope_sha256_hex`、`message_hex`、`sig_b64url`；`signInvalid[]`：S ≥ L、非规范 R、错消息、错公钥、错 epoch。
- `hlc[]`：`state`、`events[]`（`local` 加 `pt`；`receive` 加远端最大值；`presend` 加 `N`、`maxSentL` 与文档）、每步 `expected`；覆盖回拨、同毫秒、计数溢出、重新盖章（全部未发出、部分已发出）、静态界限。
- `merge[]`：`a`、`b`、`expected`；覆盖同 HLC 不同载荷、缺项、各类别超上限及其平局规则。
- `size[]`：接近 `P` 的文档、按第 6.7 节裁掉最旧墓碑后的期望文档、裁完仍超的情形（期望「拒绝」）。
- `projection[]`：`doc`、`expected.favorites`（有序）、`expected.blocked`（有序）、`expected.vetoed`、`expected.settings`。

## 19. 待用户裁决

以下取舍正文已按建议写入，用户可以改：

1. 加入时本机收藏与云端屏蔽冲突，按屏蔽处理（与平局屏蔽胜一致），确认页写出数量。
