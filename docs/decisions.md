格式：背景、决定、理由与代价。已落地的决定不改写，推翻时追加新条目并在旧条目末尾注明被取代。

## ADR-001 代码共享方案 C′：两个 Xcode 目标直接编译共享源码（2026-11-17）

- 背景：iOS 版要复用 macOS 版的模型、播放与界面，同时保持 macOS 版的编译方式与行为不变。
- 备选：A 全靠 `#if os`（平台判断散到各处）；B 全部做成 SwiftPM 包（要改 macOS 的编译方式，还要给大量成员加 `public`）。
- 决定：选 C′。`Vela`（macOS）与 `VelaPhone`（iOS）两个 Xcode 目标直接编译 `Shared/` 与 `Sources/VelaCore/`；SwiftPM 只多一个 `VelaRelay` 目标（路径 `Shared/Relay`，只含 `PlaylistRelay`，依赖 `VelaCore`），用来在 `swift test` 里跑真实回环端口测试。`PlayerController` 与 `SiteSidecar` 放 `Shared/Playback`，不进 SwiftPM。
- 平台差异：同名符号在 `App/`（多数为 `*+Mac.swift`）与 `iOS/*+Phone.swift` 各写一份，每份只登记进自己的目标；共享代码直接用这个名字，不写 `#if os`、不加协议。`Shared/` 不得依赖 AppKit / UIKit / Carbon，有 grep 门禁（见 `docs/ARCHITECTURE.md` 第 1 节）。
- 理由：macOS 的编译方式与成员可见性不变，风险最小；没有为跨模块访问而批量加 `public`；平台差异落在文件边界上，编译期就能发现漏实现。
- 代价：Xcode 工程要显式登记每个源文件（`Shared/` 与 `Sources/VelaCore/` 两个目标各登记一次），新增或重命名后必须跑 `xcodebuild`，`swift test` 发现不了漏登记；`Shared/Stage` 与 `Shared/Playback` 没有 SwiftPM 测试，只能靠 `xcodebuild` 与 `VelaCore` 下沉的纯逻辑保证。`VelaRelay` 的源码与测试整个文件包在 `#if canImport(Network)` 里，使 Linux 上也能编译。

## ADR-002 两路共享站点级状态（2026-11-17）

- 背景：iOS 竖屏双窗有两路播放（`primary`、`secondary`）。两路都要访问同一个站点，有一批状态是否按路隔离需要定下来。
- 决定：以下状态两路共享，不按路拆分：`feed`、`taste`、`curation`、`watchLedger`、`PreparedCache`、侧车、`sidecarUntil`（侧车冷却）、`challengeGate`、`EndpointBackoffBox`。toast 与收藏提示跟随焦点路。
- 代价（接受）：一路被限流，另一路会连带进入退避。具体是 `EndpointBackoffBox` 的 30 秒非 JSON 退避、`sidecarUntil` 的侧车冷却、`challengeGate` 的连续质询次数，都按接口或按站点记，不分路。
- 理由：两路面对的是同一个站点、同一个出口 IP，站点的限流与质询判定本来就不分路。分路记账只会让一路在另一路已被拦住时继续撞同一堵墙，既浪费请求又加重限流。
- `PreparedCache` 的键是用户名加档位上限：只在热状态降档前后，缓存里按旧上限预取的地址与新上限失配，会多一次重新解析；这是预期行为，不当成缺陷。
- 影响：定位「两路同时卡住」时先看这几处共享状态，不要当成两路各自的故障。

## ADR-003 实跑门口径（2026-11-17）

- 背景：App 层改动无法靠单元测试验证性能，合并前须在本机实跑 `scripts/perf-probe.sh` 并用 `scripts/perf_gate.py` 对基线判定。第一版口径在真实数据上误报或漏报，2026-11-17 用同一构建的多轮实测校准。
- 决定：
  1. CPU 看自身：`cpu_app = cpu_avg − vtdecoder_cpu_avg`，要求不超过基线 `cpu_app × 1.15 + 0.3` 个百分点；总 `cpu_avg` 只打印不判。
  2. 起播：`startup_to_play_s > 0` 且不超过基线中位数 + 1 秒；基线缺中位数时退回单值并打印警告。
  3. wakeups 只作 idle 门（绝对阈值，不放宽）；play 场景只打印，`cpu_avg > 0` 而 wakeups 恰为 0 仅在 stderr 警告，不拒绝。
  4. 实测一律经 `ssh localhost` 回环运行；基线取同一构建 play 共 5 轮的中位数。缺字段、NaN、`skipped`、`samples=0`、起播不大于 0 一律不合格，`runtime_issues` 必须为 0。
- 证据摘要（2026-11-17，`origin/main` 构建，Release，静音，各轮 60 秒，详见 `docs/PERF.md`）：
  - 各房间码率不同，硬解 XPC（`vtdecoder`）的 CPU 在 1.6% 到 2.0% 间波动，会淹没 App 自身的变化，所以只比自身 CPU；基线 5 轮中位数 `cpu_avg` 2.42%、`vtdecoder` 1.59%、`cpu_app` 0.81%。
  - 同一份代码单轮起播波动约 1.1 秒以上，其中一轮 4.51 秒疑似断流重连，单值加 0.5 秒会误判；改用 5 轮中位数 1.74 秒加 1 秒。
  - wakeups 在 main 自身 5 轮里是 0.0 到 24.0 的双峰（工具 shell 里的 3 轮是 3.2、16.0、24.9），与码流对应的网络入量（约 11 与 35 MB/min 两档）有关的可能性最大，未做对照，不适合当 play 门；idle 下数值稳定（锁屏后约 20 秒内 0.5/s），保留作门。
  - 工具里的 shell 被降优先级只跑能效核，CPU 只有约 27% 性能，wakeups 可能读成 0；与 `ssh localhost` 回环对比后确认须走回环。并行跑模拟器会污染读数，先前一版（play wakeups 0.0、idle 6.0/s）因此作废。
- 代价：play 场景的唤醒回退不会被拦住，只能靠 idle 门与 `cpu_app` 间接发现。

## ADR-004 仓库迁到公开仓，CI 用 GitHub 运行机，播放实测留本机（2026-11-17）

- 背景：项目从私有仓库迁到公开仓 `huhuhulululu/vela`，要用 GitHub 提供的 macOS 运行机做持续集成。
- 决定：
  1. 迁移用快照历史：公开仓首个提交是迁出时的代码快照，之后的提交作者应使用 GitHub noreply 地址，不暴露个人邮箱（feat/ios 分支上早期提交仍带旧作者，合并前须核对，见 PR 说明）。
  2. 公开仓禁写内容：本机绝对路径、个人邮箱、开发团队 ID、私有网络名与内部主机别名、凭据与令牌、任何真实用户数据都不得进入代码、文档、提交信息与 PR。新文字提交前自查，旧文字发现即清。
  3. CI 交给 GitHub 的 `macos-latest` 运行机，只跑编译与逻辑测试：`swift test`、实跑门负样本回归、macOS Debug 与 Release 构建、iOS 模拟器构建与测试（不签名）。
  4. 播放实测（起播、CPU、唤醒、流量）留在本机，不进 CI。
- 理由：数据中心 IP 访问目标站点会被限流或质询，结果不可复现；且在公共运行机上批量请求第三方直播内容有内容条款风险。编译与纯逻辑测试不触网，适合放 CI。
- 代价：性能与播放回归只能靠本机手动实跑与 ADR-003 的门，CI 全绿不代表播放正常；合并 App 层改动前仍须本机实测。

## ADR-005 实跑门改用固定测试流，CPU 取主进程口径（2026-11-17）

- 背景：审计发现 ADR-003 的口径有三处问题。1) `perf-probe.sh` 的 `cpu_avg` 只统计 Vela 主进程，`VTDecoderXPCService` 是独立进程、单独统计，而门里的 `cpu_app = cpu_avg − vtdecoder_cpu_avg` 把两个进程相减，另一个进程的负载会抵消主进程的回退（错误口径）。2) 采样失败（`top` 找不到进程、`footprint` 失败）补 0 仍计入 `samples`，会空成功；脚本提前退出时不删旧结果文件，调用方可能读到上一轮的结果。3) 每轮随机直播房间，码率不同，主进程 CPU 跟着码率变（本次对照：11 到 37 MB/min 的三轮，cpu_avg 2.83 到 3.16），活直播不适合做回归门。
- 决定：
  1. 撤销 ADR-003 第 1 条里「扣除硬解」的部分：play 的 CPU 直接比较主进程 `cpu_avg`，不超过基线 × 1.15 + 0.3 个百分点；`vtdecoder_cpu_avg` 只打印。
  2. 回归门一律用固定测试流（`perf-probe.sh --fixed-stream`）：本机合成 HLS（1920x1080 30fps，约 3.1 Mbps 固定码率，视频档加独立音轨），由 `serve-test-stream.py` 在 127.0.0.1 提供；App 在 DEBUG 或 PERF_PROBE 构建里识别 `--perf-stream <地址>`，跳过目录与站点解析，其余走正常的中继与 `PlayerController`。基线与结果都必须是固定流模式（JSON 记 `stream_mode`、码率），模式不同拒绝比较。活直播只作观察。
  3. 采样失败记无效样本，不补 0、不计入 `samples`；无效占比 > 10% 或有效样本 < 5 即非 0 退出；门拒绝 footprint = 0、app_size = 0、样本数与时长不符；探针开头先删旧结果文件。
  4. Release 产物不得含该钩子：CI 的 Release 构建后跑 `scripts/check-release-no-perf-hook.sh`。检测依据是钩子里的长标识串与类型名，因为 Swift 把 15 字节以内的字符串编进指令，`strings` 搜不到 `--perf-stream` 本身（只搜它会假通过）。
  5. 占用检测与 `selftest.sh` 同一写法（按进程命令开头匹配），`--fixed-stream` 下每 30 秒等一次，最多 90 分钟；不匹配 `selftest.sh` 本身，因为它等占用时也会等 `perf-probe`，两边互等会死锁。
- 例外：钩子的两处调用（`StageModel.swift`、`StageModel+Playback.swift`）用了 `#if os(macOS) && (DEBUG || PERF_PROBE)`，违背 ADR-001「共享代码不写 `#if os`」。原因是钩子实现只在 macOS 目标里（`App/PerfStream+Mac.swift`），iOS 的 Debug 构建没有这个符号；不为一个调试钩子给 iOS 再加一份空实现。
- 证据（同一构建，60 秒各 3 轮，详见 `docs/PERF.md`）：固定流 cpu_avg 2.71、2.46、2.79（均值 2.65，样本标准差 0.17）；活直播 2.83、3.04、3.16（均值 3.01，样本标准差 0.17）。**两组标准差在 3 轮里没有明显差别**，固定流的收益是去掉码率与房间的混杂、免受外部断流重连与站点限流影响，而不是 3 轮就能看出的离散度下降；要量化需更多轮次。
- 代价：固定流是合成画面，不含真实站点的编码特征与网络抖动；中继的续期、403 路径测不到，仍靠 selftest 与人工实测。基线只覆盖 3 轮，噪声约 0.15 个百分点，门限 0.7 个百分点内可用。


## ADR-007 双窗画中画：只在焦点路挂一个控制器，进入时释放另一路（2026-11-18）

- 背景：计划修订 A3 记下 PR0 Spike 在 iPad 模拟器上的现象：双窗回桌面 4 次未能自动进入画中画，手动 `startPictureInPicture()` 报 `AVKitErrorDomain -1001`；同一轮日志里每路都有重复的视图与控制器。单窗在同一台模拟器上稳定进入。T18b 要求：只有焦点路可进画中画，进入时释放另一路，回 App 恢复双窗；3 秒内没进入就按无画中画处理（全停释放，不留后台播放或黑小窗）；并查清根因。
- 排查：正式实现里分别用启动参数（仅 Perf 构建）打开或关闭怀疑项，iPad Pro 11 英寸（M5）模拟器、固定测试流（两路共用同一个本机合成流，不访问站点）、静音，每组 1 到 2 轮。「联网」按测试流服务端的响应字节统计（`serve-test-stream.py --stats-file`；回环流量不进 nettop，nettop 读数恒为 0，不能当证据）。

| 组 | 配置 | 结果 |
|---|---|---|
| A | 正式实现：只给焦点路的播放层挂一个控制器，回桌面自动进入 | 两轮都 `pip started`；回桌面后只剩焦点路联网（服务端 21.6 与 21.5 MB/min，前台两路 47.4 与 42.9），回前台 `pip stopped restore=true`，两路恢复首帧 |
| B | 同 A，但进入时不先释放另一路（`--perf-no-pip-solo`） | 仍 `pip started`。区别只是回桌面后前几秒两路都在联网（40.6 MB/min），随后由进后台流程释放另一路（23.0 MB/min）。所以「进入前先收起为单窗」不是进入成功的条件 |
| C | 每一路的播放层都挂控制器（`--perf-pip-all-lanes`），回桌面自动进入 | 系统开始进入（`willStart`）后既没有 `didStart` 也没有 `failed`，卡在启动中；进后台流程判定不能继续，全停并关掉小窗（`pip stopped restore=false`），之后服务端零请求、CPU 0.3% |
| D1 | 前台手动启动，单控制器 | `pip attach` 一次，`pip possible=true`，调用后 `pip started` |
| D2 | 前台手动启动，每路各一个控制器 | `pip attach` 两次，`pip possible=true`，调用 `startPictureInPicture()` 后没有任何委托回调（既无 `didStart` 也无 `failed`），没有进入 |

- 结论：根因是同一时刻存在不止一个 `AVPictureInPictureController`（每路一个）。此时系统既不进入、也不回报错误（自动与手动两条路径一致）。只保留一个、且绑在焦点路播放层上的控制器后，双窗自动进入与手动进入都成功。Spike 里的 `-1001` 这次没有复现：C、D2 的现象是「没有任何回调」，与 Spike 的错误码不同；两者同属「多个控制器并存时不能进入」，但 `-1001` 本身未证实是同一机制，只在模拟器上验过，待真机复核。
- 决定：
  1. 只给焦点路的 `PlayerLayerView` 传画中画控制器（`PhoneRoomPage.carriesPictureInPicture(lane:focus:)`）。`PictureInPictureCoordinator` 是单个对象、同一时刻最多一个系统控制器，焦点切换时由新焦点路的播放层接过去。
  2. 画中画开始（`willStart`，含前台按钮与回桌面自动进入）时只留焦点路，另一路立刻释放（与横屏同一套 `applyLaneVisibility`）；结束或启动失败后恢复双窗。小窗开着（或在启动）时焦点不能换（`focusLocked`），因为小窗里放的就是焦点路。回前台时若小窗已收掉就放开，小窗还在收的由 `didStop` 放开。
  3. 回桌面自动进入的 3 秒回退不变（`PiPFallback`）：3 秒内不在 `.active` 就全停释放、关掉可能半开的小窗；双窗下两路都释放。
  4. 日志加 `pip attach`、`pip possible=<值>`，以后再出现「进不去」时先看有几次 attach。
- 代价：画中画期间焦点路必须保持联网与解码，另一路在小窗关闭、回到 App 后才重新起播，会有一次重新解析与首帧。

## ADR-006 双窗停留口径、热降档与流量取舍（2026-11-18）

- 背景：iOS 竖屏双窗同时联网、同时解码。用户裁决 3：两路都用最高档、不封顶；热状态到 `.serious` 及以上时两路降档，回落到 `.fair` 及以下并持续 60 秒后回升；流量约翻倍是明确的取舍。计划 §4.3 同时规定了停留的结算口径。
- 决定：
  1. **停留口径**：每路各记一份停留，结算时带原始秒、加权秒（焦点段 1.0、非焦点段 0.5）、焦点秒、结束原因与本路自己的来源（`LaneSettlement`，`DwellTracker` 记焦点秒）。口味学习：原始秒满 3 秒才用加权秒打分；不足 3 秒只有结束原因是 `.swipe` 时才记弱落空。每日命中率只看焦点秒：从没有焦点的路不进；焦点路上还没出画面（0 秒）就划走仍记一次落空，与单窗原口径一致。观看账本记加权秒（暂停学习时段先扣，再按加权秒与原始秒的比例折算）。`.background` 与 `.dualOff` 结束的停留不产生落空，回前台或重开双窗后另开一段。热门关联与常看收藏提示只跟焦点路。单窗焦点恒在这一路，三个秒数相等，口径与原来一致。
  2. **与旧口径的差别**（计划 §4.3 的明文规定，不是副作用）：换来源（`.sourceChange`）与进后台（`.background`）结束的停留，不足 3 秒不再记弱落空；原先 macOS 与 iOS 单窗都会记。 同理，自动跳过（`.autoSkip`，失败后沿原方向跳到下一间）结束的停留，不足 3 秒也不再记弱落空：macOS 的行为因此变化。该停留在播放失败时本就被 `markFailed` 排除，实际受影响的只有「房间刚起播就被自动跳过、且没有失败标记」的少数情形；计划 §4.3 只把 `.swipe` 列为记弱落空的结束原因，所以按计划执行，不改代码。
  3. **热降档**：`LaneQuality` 按每路画面实际显示高度（`displaySize`，不是窗格高度）乘显示倍率查档，下限 896 kbps；iPhone 竖屏双窗里 16:9 画面约 221 点 × 3 = 663 像素，降到 1.696M 档。还没有画面尺寸时落到下限。降档与否一变，在播的路现取主列表、选档、原地换档；没有播放项的路下次起播带新上限。回升检查只在「降档且已回到 fair 及以下」时排一次性任务，再发热即取消，不留空转定时器。macOS 不订阅热状态。
  4. **流量取舍**：两路都用最高档，网络约为单窗的两倍。固定测试流（1080p，平均 3.10 Mbps，两路合计 44.4 MB/min）的服务端实测：双窗 45.2 到 47.3 MB/min，是所选档位带宽之和的 1.02 到 1.07 倍；画中画只留焦点路时 21.5 MB/min。真实站点最高档按 `docs/PERF.md`「iOS Spike」的 5128k 档约 38 MB/min 估算，双窗约 76 MB/min（约 4.5 GB/小时），单窗约一半；这个估算没有在真实站点上实测。用户已明确选择不封顶，这里只记账；本版不加蜂窝网络提示，也不设流量上限。保护只有热状态降档。
  5. **失败分类**：损坏码流（垃圾 mp4、截断的 mp4、垃圾 mov）在双窗副路也判为房间失败，不是「双窗不可用」；只有白名单码（`decoderTemporarilyUnavailable`）才降级释放副路。样本由真的 `AVPlayerItem` 读出错误链（`FailureSampleTests`）。
  6. **Perf 钩子范围**：ADR-005 的 `#if os(macOS)` 例外扩到 iOS 的 Perf 配置：共享代码里的调用写成 `(os(macOS) && (DEBUG || PERF_PROBE)) || (os(iOS) && PERF_PROBE)`，实现在 `iOS/PerfStream+Phone.swift`，Release 产物不含（安全门搜长标识串）。模拟器里回环流量不进 `nettop`（读数恒 0），联网与否改按固定流服务端的响应字节统计（`serve-test-stream.py --stats-file`）。
  7. **测试隔离**：`StageModel` 的口味、收藏、观看记录写在模拟器沙盒的固定位置，用例之间会累加；双窗用例经 `TestPrefs` 造模型，用例前后落盘并删文件，命中与落空只比增量。
- 代价：加权口径让双窗里的非焦点观看对口味的影响减半，副路换得越勤、学习越慢；流量与解码开销约翻倍，靠热状态降档兜底，没有真机热数据。
- 被部分取代（2026-11-18，ADR-008）：第 3 条「热降档按画面显示高度查档」改为 ADR-008 第 3 条的三层上限（两路时热降档以最高档为基准逐档下降）；第 5 条的「双窗不可用」文案与「主路永不降级」改为 ADR-008 第 4 条（焦点路受保护、显示「资源不足」）。其余各条不变。

## ADR-008 iOS 三窗：最多 3 路，减路数保留焦点并压紧，三格按格子尺寸选档（2026-11-18）

- 背景：用户裁决最多 3 路、iOS 先做、macOS 维持单窗。计划 `docs/plans/ios-triple.md` v1 与修订 v2（对抗审查 12 条的裁决）规定了需求边界与验收；本条记实现时定下的取舍与实测。
- 决定：
  1. **两套路身份同时扩**：`LaneID` 与 `PlaybackLaneRole` 都加 `tertiary`，一一映射（`LaneID.role` / `PlaybackLaneRole.laneID`），日志标签统一为 `label`。`LaneSelection` 改为一次分配内维护动态占用集合，其他各路当前房间是硬约束，替补顺序 P → S → T，候选不够时焦点路优先、空格留给非焦点路；新增 `.fill`（开新路沿前一路往后补位）。两路的既有选房测试不改、全部通过，两路行为不变。
  2. **路数三层状态与减路数**：用户选择（`SettingsStore.laneCount`，旧 `phoneDual` 只在新键不存在时迁移）、逻辑路（`lanes`）、允许播放的路（`visible` 与闸门）分开。横屏与画中画只临时释放播放资源。减少路数保留焦点路、按 P → S → T 补足名额，被移除的路以 `.layoutChange`（原 `.dualOff` 改名）结算后丢弃；保留 P、T 时第三路的 `PlaybackLane` 对象整体换身份成副路（`reassign(to:)`），播放器与在途任务不动、不重新起播；只留一路时沿用原双窗关闭的做法（先切声音到主路，再把焦点房间搬到主路，主路重新起播一次）。主路始终是 `feed.current` 的那一路，不做主路身份迁移。
  3. **画质三层上限**（取代 ADR-006 第 3 条）：最终上限 = min(尺寸上限, 热上限)。1、2 路尺寸上限不限（维持裁决 3）；3 路按每格画面实际显示的像素高度经 `PowerPolicy` 选档，还没出画面时按格子里 16:9 画面估算，横屏与画中画只显示一路时视为不限。热上限 serious 降一档、critical 降两档，以尺寸上限为基准沿 896k / 1.696M / 3.096M / 5.128M 下降，最低档保持；连续 60 秒 fair 以下回升到尺寸上限。换档只在上限真变了时原地进行，回升用一次性任务，不新增定时器。实测（多档固定流 1080p 3000k / 720p 1200k / 540p 600k，模拟器，静音，`docs/PERF.md`「iOS 三窗」）：iPhone 17 Pro 三格每格 402x290 点、画面 402x226，三路都选 720p，服务端 25.9 MB/min；同机两路选 1080p，44.7 MB/min；iPad Pro 11（M5）三格 834x402、画面 715x402，选 720p，27.0 MB/min。起播档位只按「离开降画质」判低档（有限的尺寸或热上限不是低档）；格子还没布局时按舞台尺寸推算格子估算，冷启动不先落最低档。
  4. **解码资源不足**（取代 ADR-006 第 5 条的文案与主路规则）：焦点路受保护；非焦点路命中白名单码才降级，显示「资源不足」，不计房间失败与重试预算；焦点路命中时按 T → S 让出一路非焦点路，自己按房间重试。恢复入口：用户重试、切房、回前台、焦点切到该路、减少路数；自动重试按 60、120、240 秒有限次退避，用完不再排（PR #8 审计：避免资源持续不足时无限「降级 → 重试」）。白名单仍只有 `decoderTemporarilyUnavailable`，损坏码流仍判房间失败（`FailureSampleTests` 锁住）。
  5. **中继源表上限 2 → 3**：`RelaySourceTable.maxSources` 改为 `LaneID.maxCount`。上限 2 时第三路登记会挤掉最旧的源，三路无法同时播放；计划没有列出这一处，实现时发现并改正，源数变化写日志 `relay sources=N`。
  6. **可用尺寸**（M12）：三格每格不足 160 点的屏幕最多 2 路，已开 3 路临时降到 2 路、不改用户选择，放得下时恢复。按这个公式 iPhone SE 尺寸（667 点高，三格每格约 221 点）放得下三格，计划里「例如 SE 尺寸」的举例与 160 点的数字不一致；按冻结区块里的数字执行，实际只有分屏等很矮的窗口会触发。
  7. **实跑工具**（M11）：固定流入口三个测试房间、`--perf-lanes N`；探针给了服务端统计文件时按服务端字节判联网（前台必须有字节，无画中画回桌面 5 秒后必须为 0，画中画期间按视频列表请求率估算只剩一路）；分析器另判首帧路数、各路两两不同、后台中继源数；负样本 `scripts/test_perf_probe_ios_analyze.py` 进 CI。
- 代价：三格时画质按格子降到约 720p（模拟器两种设备都是），比两路少约三成流量但不是最高档；只留一路时焦点房间要在主路重新起播一次；画中画进出时焦点路会原地换一次档（尺寸上限在不限与按格子之间切换）。模拟器用宿主机解码，不能证明 iPhone 三路硬解能力，真机三路持续播放待用户在 TestFlight 上确认。
- 补记（2026-11-18，PR #8 审计修复）：多路快照的主路取可见列表里的 `currentUsername`（可为空），不再用 `feed.current` 的首间回退值，否则主路为空时另一路向前划会同房；热降档按降档档数变化换档（serious 升到 critical 也换）；画中画期间路数菜单禁用并说明原因，结束后补判舞台尺寸；三格判定只用竖屏实测尺寸，启动时尺寸量到之前最多开 2 路。

## ADR-009 iOS 真机诊断：MetricKit 每日摘要只存本机（2026-11-18）

- 背景：用户要求「低耗、轻、性能稳定」，模拟器拿不到真机的耗电、发热与三路硬解数据（ADR-008 的边界）。需要一个不打扰、不外发的真机数据来源。
- 决定：
  1. 用系统 MetricKit（`MXMetricManager`）订阅每日的 `MXMetricPayload` 与 `MXDiagnosticPayload`，启动时订阅一次，回调由系统投递，不新增定时器与常驻任务。
  2. 解析在 Core（`DiagnosticDigest`，按 `jsonRepresentation()` 的 JSON，键名递归查找、带单位字符串换算），可在 SwiftPM（含 Linux）里测试；同日新指标替换、诊断计数累加，只留最近 7 天，原始 JSON 截到 256 KB 一并保存。
  3. 存在 `Application Support/Vela/diagnostics.json`（目录排除 iCloud 备份）；不联网、不上传、不同步。界面只有口味面板底部默认收起的「诊断」，展开时才读文件；「复制为文本」只复制摘要，「分享」经系统分享表附原始 JSON，发不发由用户决定。
  4. MetricKit 不按前后台拆 CPU 时间：摘要给总 CPU 时间与前台、后台运行时长；崩溃、卡顿、CPU 与磁盘写入异常取当天诊断 payload 的条数，异常退出取指标里各类异常退出计数之和。
- 代价：Release 主二进制增加约 87 KB（`docs/PERF.md`「真机诊断」）；系统大约每天才投递一次，新装后至少要等一天才有数据；iOS 没有单独的设置页，入口放在口味面板底部。


## ADR-010 macOS Release 用 -Osize（2026-11-19）

- 背景：站点抽象与 Cam4 接线后，macOS 的 PERF_PROBE Release 为 4184 KB，探针读数 4.1，超出体积门 3.7 + 0.3 MB；用户要求体积门不放宽、不牺牲播放热路径 CPU。
- 决定：只对 `Vela` 目标的 Release 配置设 `SWIFT_OPTIMIZATION_LEVEL = -Osize`；Debug、Perf、`VelaPhone` 与工程级配置不动。
- 依据（`docs/PERF.md`「macOS 体积门与 Release -Osize」）：可执行文件 2,593,616 → 2,350,784 字节，`.app` 3944 KB（读数 3.9，比 main 还小 4 KB）。G-mac 三轮中位数 CPU 1.93% → 1.70%（复测 1.65%），footprint 不变，起播中位数 1.83 秒，idle 为 0。不改全局设置的办法（冷路径 `@_optimize(size)`、轻量 JSON 解析、码表压缩、禁止内联）合计最多省 16 KB，不够过门，已撤回。
- 代价：以后 macOS Release 的热路径也按体积优化，CPU 是否回退要靠每次 G-mac 判；Debug 与 Release 的优化级别差异更大。若某次 G-mac 显示 CPU 回退超过 5%，再考虑对热路径函数单独 `@_optimize(speed)`。
